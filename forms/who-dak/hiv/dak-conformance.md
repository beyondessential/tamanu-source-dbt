# DAK conformance

What these forms take from the WHO DAK, what they deliberately do differently, and what the DAK
specifies that a Tamanu form cannot hold.

## Source

Everything is generated by [`dak_generator.py`](../dak_generator.py) from **Web
Annex A**, the DAK's data dictionary (`WHO-UCN-HHS-SIA-2023.27-eng.xlsx`, 2,094 rows across 12
`HIV.*` process tabs). Annex A gives each data element an ID (`HIV.D.DE39`), a label, a data type,
a `Required` flag, terminology codes (ICD-11 / ICD-10 / LOINC / ICHI / ICF / SNOMED GPS), the
Annex C indicators it feeds, and — for coded elements — one child row per input option
(`Multiple Choice Type = "Input Option"`), which is where the exact option strings live.

Four further prompts come from **Web Annex B**, the decision-support logic. Nothing is authored by
hand.

## What the forms are

Ten surveys, one per DAK business process: 259 questions from the dictionary plus 6 decision-support
prompts, over 48 screens.

| | |
|---|---|
| Questions carrying a DAK data element id | 259 of 259 |
| Coded questions carrying Annex A's options | 95 of 95 (481 options) |
| Mandatory | 85 — exactly the DAK's `Required = R` |
| Linked to an Annex C indicator | 160 |
| Label / option / mandatory mismatches against the dictionary | 0, verified on every build |

- **Question codes** carry the DAK id: `HIV.D.DE39` → `whodakhiv-d-de39`. Hyphens, because an id
  may hold only alphanumerics and `-` (*"id must not have spaces or punctuation other than -"*) and
  the code is embedded in the `pde-<code>` id built from it. The cost is that these codes cannot be
  referenced from a math.js `calculation`, where `a-b` is subtraction, so a calculated question
  needs a separator-free code of its own.
- **Labels and option strings** are Annex A's, verbatim. Option strings are what land in
  `survey_response_answers.body`, so nothing downstream can compensate for strings that do not
  match the dictionary.
- **Screens are the DAK's own activities**, one per activity in process order (`HIV.D1` →
  `HIV.D29` for the care visit).
- **`HIV.I Referral` is Tamanu's `referral` survey type**, so it lands on the facility Referrals
  tab; the rest are `programs`.
- Each question carries a `_dak` block in the spec — data element id, activity, data type, why it
  was selected, and its indicator links. That is the crosswalk source, and is not written to the
  workbook, which has no column for it.

### The selection rule

Annex A's ten form-bearing tabs hold 829 parent elements — the HIV.D pair alone holds 361. No form
can carry all of them, so an element is included when it is any of:

1. `Required = R` — the DAK says a system must capture it;
2. linked to an Annex C indicator — it feeds something reported;
3. named in Component 5 Table 11 — the DAK's own core shortlist.

That yields 259. Rule 3 applies only to the HIV.D tabs, since Table 11 is the only place the DAK
itemises a shortlist, and it exists because rules 1 and 2 alone drop **HIV clinical stage**
(`Required = O`, no indicator link). Ten further HIV.D elements are named explicitly in [`domain.py`](domain.py): blood pressure (`DE14`, `DE15`) and the rest of the vital signs, without which the
vitals screen is body weight alone; the prescribing decision (`DE444`); reasons for adherence
failure (`DE197`); adherence counselling (`DE465`); and MUAC (`DE884`), the DAK's measurable proxy
for nutritional status.

The rule bites unevenly, which is worth knowing: it keeps 40 of 132 elements on the HTS visit but
11 of 12 on referral, because referral is almost entirely `Required = R` while HTS carries a long
tail of optional detail.

## Deliberate divergence

**Eight coded elements have no option list in the dictionary** and are emitted as free text rather
than having a list invented for them: `HIV.A.DE13` country of birth, `HIV.A.DE43` administrative
area, `HIV.B.DE66` HIV diagnosing facility, `HIV.B.DE201` adverse event severity, `HIV.D.DE75`
current ART regimen, `HIV.D.DE444` ART regimen prescribed, `HIV.D.DE457` medications prescribed,
`HIV.D.DE604` vaccine type. The DAK leaves these country-configured (Table 13). A deployment should
replace them with a local coded list, or in several cases an `Autocomplete` over existing Tamanu
reference data — country of birth, administrative area and diagnosing facility all have natural
Tamanu sources.

**Two of Annex A's twelve `HIV.*` tabs are not forms.** `HIV.Surveillance` defines no data elements
of its own — its rows re-list other processes' elements as a cross-cutting reporting view, so it
belongs with the metric layer. `HIV.Configuration` is deployment constants: population prevalence
of TB, population HIV incidence, prevalence of pretreatment NNRTI resistance, malaria-endemic
setting. One value per deployment, read by the decision logic, and wrong to model as patient data —
these belong in Tamanu settings or a dbt seed.

**`HIV Registration` duplicates the Tamanu patient record.** The DAK defines the process, so the
survey is generated for completeness, but first name, family name, address and telephone number as
survey questions are the anti-pattern Tamanu forms exist to avoid. Either drop that survey or
convert its demographic questions to `PatientData` reads — a deployment decision, left open rather
than guessed at.

**The registry is not from the DAK.** Program registries are a Tamanu construct with no DAK
equivalent; its clinical statuses and conditions are our own modelling of the HIV cascade. See the
[the domain README](README.md).

## Decision support (Annex B)

Annex B holds 13 decision tables and 4 scheduling tables. Its input columns are the test of what
can be encoded: of **83 inputs, 35 are questions these forms carry and 46 are not** — and the
misses are structural rather than accidental.

| The 46 misses | Example inputs | Where they belong |
|---|---|---|
| Values a rules *engine* holds between decisions | `Established on ART`, `Suitable for PrEP`, `Switch to second-line ART regimen recommended`, `Assay number in testing strategy` | Nowhere in a survey — a form has no working memory; these are outputs of one table feeding another |
| Deployment constants | `HIV burden of the setting`, `TB screening algorithm` | Tamanu settings or a dbt seed — these are the `HIV.Configuration` tab, which is why it is not a form |
| Derived values | `Estimated creatinine clearance`, `Persistent CD4 count` | Reporting layer, over submitted answers |
| Annex A elements the selection rule does not reach | `Currently on PrEP`, `PEP history`, `Acute HIV infection symptoms`, per-assay test results | `CORE_ELEMENTS` in [`domain.py`](domain.py), if a deployment needs them |

**A form can prompt; it cannot conclude.** That is where the encodable subset stops, and
`HIV.D17.DT.01` shows why: it fires on *"viral load > 1000 copies/mL **based on two consecutive
viral load measurements three months apart, with adherence support following the first**"*. The
threshold is checkable inside one submission; the history is not. Encoding it as though it
concluded `Treatment failure = 'Virological failure'` would assert something the form cannot know,
so the guidance carries the DAK's qualifier and leaves the judgement with the clinician.

### What is encoded

Four additions on the care-and-treatment visit, each marked `_decisionSupport` in the spec with the
Annex B rule it came from, and each placed immediately after its trigger question so the prompt
lands on the same screen as the answer that raised it.

| Rule | Type | Fires when | Effect |
|---|---|---|---|
| `HIV.B2.DT.01-05` | `Instruction` | any of the 5 danger signs Annex B lists for 10 years and over | shows "immediately take action or refer for care" |
| `HIV.B2.DT.01-05` | `PatientIssue` | same gate | raises a Tamanu patient **warning** |
| `HIV.B2.DT.06-14` | `Instruction` | any of the 8 danger signs Annex B lists for under 10 years | the same guidance, naming the age band |
| `HIV.B2.DT.06-14` | `PatientIssue` | same gate | raises a Tamanu patient **warning** |
| `HIV.D17.DT.01` | `Instruction` | viral load ≥ 1000 copies/mL | prompts evaluation for virological failure, naming the two-measurement rule |
| `HIV.D17.DT.03` | `Instruction` | CD4 ≤ 250 cells/mm³ | prompts evaluation for immunological failure and advanced HIV disease |

`HIV.B2.DT` is one decision table of fourteen rules, split by age: rules 01-05 apply at 10 years
and over, 06-14 under 10. A visibility gate cannot read age — it lives on the patient record, not
on the form — so the table becomes two prompts, one per band, each naming its band in the
guidance. Three signs appear in both bands (Annex B's own rules 01/02/05 and 12/13/14), so a
client with tachycardia sees both: two prompts on a danger sign is the right failure. Taking the
union instead would put the criteria at 270 characters against a `varchar(255)` column, and
trimming signs to fit is what left convulsions and a fever of 39 °C ungated.

A gate value must match Annex A's option labels exactly or the guidance silently never appears, so
the generator errors on a gate value that is not an option of its target question rather than
emitting a rule that cannot fire.

`--no-decision-support` omits all four, generating from the data dictionary alone.

### What is not encoded

- **The assay-sequence algorithms** (`HIV.B7.DT`, `HIV.E4.DT`, `HIV.E12.DT`) loop over repeated
  test results carrying an assay counter. Stateful, so not expressible in a form.
- **`HIV.D15.DT` clinical staging** — 66 rules mapping a condition/symptom list to a stage. The
  input element (`WHO HIV clinical stage condition or symptom`) is not captured, and a form cannot
  compute the mapping. The clinician-entered stage (`HIV.D.DE186`) stands instead.
- **`HIV.D21.1/21.2` ART regimen and drug interactions** — 33 and 64 rules against regimen
  composition. A lookup table, belonging with reference data or Tamanu's medication features.
- **`HIV.C7.DT` PrEP suitability and `HIV.C23.DT` PEP regimen** depend on derived inputs the form
  does not hold.
- **The four scheduling tables** (`HIV.S.1`–`S.4`) define when the next contact is due: recommended
  services, ART response monitoring, cervical-cancer screening intervals, retesting. Recall and
  appointment concerns — Tamanu appointments, the registry's loss-to-follow-up threshold, and a
  `metric__` model for "due for viral load" — not form content.

## Annex D

71 functional and 70 non-functional requirements, written as user stories (*"As a … I want … so
that …"*). Nothing to encode in a form: it is a conformance checklist for the deployment as a whole
— audit trails, offline capability, role-based access, notifications. Worth reading before anyone
claims DAK compliance, since most of it is Tamanu platform behaviour rather than anything this repo
configures.

## Known gaps, in priority order

1. **Conditional visibility is almost absent.** Annex A expresses conditionality as prose in
   `Explain Conditionality` plus a `Required = C` flag, which does not translate mechanically into
   `visibilityCriteria`. Each form therefore asks nearly every one of its questions every time,
   where the DAK intends much of it to appear only when relevant. The four Annex B prompts are the
   only gated questions. Closing this needs the conditionality prose read element by element, and
   it is the single biggest thing outstanding.
2. **`HIV.D8` is the care visit's largest screen at 14 questions**, including TB history items that
   read as though they belong with `HIV.D4` "Screen for TB". This is the dictionary's own grouping,
   reproduced rather than improved on — worth revisiting with a clinician.
3. **Visit date sits on the registration form** as `HIV.A.DE3`, because that is where Annex A puts
   it. A clinician filling only the care visit records no visit date; Tamanu stamps a submission
   date, but an explicit one on each encounter form is usually wanted.
4. **No calculated elements.** The DAK's calculated data elements live in Component 5 Table 12, not
   in Annex A's process tabs, so nothing here generates them. BMI, virally suppressed, established
   on ART and estimated creatinine clearance all depend on history a single submission cannot see,
   and belong in the reporting layer.
5. **Cross-process elements sit in their own form**, which is correct but worth knowing when
   reading one form in isolation: key population (`HIV.B.DE49/50`) and partner HIV status
   (`HIV.B.DE33`) are on the HTS visit; serum creatinine (`HIV.C.DE72`) is on the PrEP visit.

## Indicator coverage

`annex_c_coverage.py` answers, from the annexe and the generated spec rather than from memory,
which of Annex C's 140 indicators these forms can compute:

```bash
cd forms/who-dak
python annex_c_coverage.py --domain hiv            # counts
python annex_c_coverage.py --domain hiv --list gap # and what each gap is missing
```

| | |
|---|---|
| Computable from the forms | **88** |
| No computable numerator — Annex C's own statement (`Not included in DAK`: survey-based, commodity stock, another system) | 49 |
| Element missing from the forms | 3, all prose fragments |

Annex C writes each numerator and denominator in terms of Annex A elements, quoted — `COUNT of
clients with "HIV status"='HIV-positive' AND "On ART"=True` — so the check is a comparison of
quoted labels against question labels, and only against questions that carry a data element:
an activity heading that happened to read like an element label would otherwise count as
coverage a deployment does not have. All three remaining gaps are prose fragments from
multi-line calculations (`"reporting date"`) rather than real elements: read the printed labels
before widening the selection.

One gap was real, and is closed. `HIV.D.DE481` "Date(s) of substitution within first-line
regimen" is not on the DAK's core shortlist and carries no indicator link, so neither selection
rule caught it — while Annex C's ART.9 numerator names it. Without it a toxicity switch on
first-line treatment was invisible and the indicator would have undercounted while still
returning a number. It is now selected explicitly, which is the one case in this build where a
DAK element is carried because an indicator needs it rather than because the DAK's own rules
select it.

**Sixteen counts over nine indicators are implemented** in `tamanu-source-dbt`'s
`metric__who_dak_hiv_indicators` — HTS.2, HTS.3, ART.1, ART.3, ART.4, ART.5, ART.9, DSD.3, DSD.4,
with ART.1 also disaggregated by key population. The remaining covered indicators are a backlog,
not an obstacle: each is a predicate over the same two intermediates.

## Terminology linkage

Annex A carries ICD-11, ICD-10, LOINC, ICHI, ICF and SNOMED GPS codes per element, and names the
Annex C indicators each element feeds — 160 of the questions have indicator links, which is what
the coverage check reads. The terminology codes are not used yet: they are the raw material for
the `map__omop_hiv_dak` crosswalk seed that architecture decision D1 prescribes ("OMOP vocabulary
lookups via `map__omop_<domain>` seeds, populated on demand only").

## Fetching the annexes

`<domain>/annexes/` is gitignored: the DAK and its annexes are third-party publications WHO
serves at stable URLs. Fetch Annex A to where the generator looks for it -- it prints this
command itself when the file is absent:

```bash
mkdir -p forms/who-dak/hiv/annexes
curl -sL -o forms/who-dak/hiv/annexes/WHO-UCN-HHS-SIA-2023.27-eng.xlsx \
    https://iris.who.int/server/api/core/bitstreams/e9b0d20e-32ab-4d66-a5b6-638d39b0b443/content
```

Reproducibility rests on the checksum rather than on the bytes being in git. These forms were
generated from sha256 `a86a726d2cbbc487c232c9b5fe3304bb2061d192efbb7bf3ab8353dd6638e40e`, which
`dak_generator.py` verifies and warns about on mismatch — so a revised annexe announces
itself rather than quietly changing a form.

That direct URL was resolved through the DSpace API, worth recording because the legacy
`/bitstream/handle/...` URLs now serve a JavaScript shell rather than the file. To find the
equivalent for another annexe — B decision-support logic `10665/375057`, C indicators
`10665/375058`, D requirements `10665/375059`:

```bash
# handle -> item uuid
curl -sL -o /dev/null -w '%{url_effective}\n' https://iris.who.int/handle/10665/375056
# item -> ORIGINAL bundle -> bitstream -> content
curl -s https://iris.who.int/server/api/core/items/<item-uuid>/bundles
curl -s https://iris.who.int/server/api/core/bundles/<bundle-uuid>/bitstreams
curl -sL -o annexA.xlsx https://iris.who.int/server/api/core/bitstreams/<bitstream-uuid>/content
```

## Rebuilding

```bash
cd forms/who-dak
FORMS_SKILL=../../../claude-plugins/plugins/tamanu/skills/build-tamanu-forms/scripts
python dak_generator.py --domain hiv
python $FORMS_SKILL/build_program_xlsx.py \
    --spec hiv/who-dak-hiv_program.json --out hiv/who-dak-hiv_program.xlsx
```

The registry is declared in [`domain.py`](domain.py) rather than carried across from the
previous spec, so a regeneration cannot lose it.
