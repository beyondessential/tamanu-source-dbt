# DAK conformance — birth defects surveillance

What these forms take from the WHO Birth Defects Surveillance DAK, what they deliberately do
differently, and what the DAK specifies that a Tamanu form cannot hold.

## Source

Everything is generated by [`../dak_generator.py`](../dak_generator.py) from the kit's **core data
dictionary** (`BDS DAK_core data dictionary.xlsx`, 265 labelled rows across the four clinical tabs
of the seven the workbook holds). It gives each data element an ID (`BDS.Comm.DE.20`), a label, a
data type, an `Optionality` flag, terminology codes (ICD-11 / ICD-10 / LOINC / SNOMED CT / ICHI /
ICF / ATC), the Annex C indicators it feeds and — for coded elements — one child row per value.

Nothing is authored by hand, and nothing comes from Annex B, which this kit does not publish.

**This kit is not published as IRIS Web Annexes.** WHO ships its components through the SMART
guidelines implementation guide at [smart.who.int/dak-bds](https://smart.who.int/dak-bds/), whose
component pages serve whatever the site last built, so [`domain.py`](domain.py) pins each
component to WHO's own source repository for that guide — `WorldHealthOrganization/smart-dak-bds`
— at the **`v1.0.0` tag**, whose `sushi-config.yaml` declares `status: active` and
`releaseLabel: release`. That is a version-pinned path to the released bytes, which the component
page is not; the component page is recorded alongside it as `page`.

## What the forms are

Three surveys: 70 dictionary questions across 12 screens, 156 option strings, 17 mandatory. The
spec holds 82 rows in all, the rest being screen headings. See the [README](README.md) for the
table.

## A value set that nests

This is the kit's structural signature, and it is a shape no other kit has.

Every other DAK's coded element is one question and a flat list of answers. This one states the
congenital anomaly as a **tree three levels deep**, and each level is a row typed as a list:

| Level | Row | Type |
|---|---|---|
| the question | `BDS.Comm.DE.20 Congenital anomaly diagnosis` | `List – select all that apply` |
| a body system | `BDS.Comm.DE.21 Central nervous system defects` | `List – select all that apply` |
| a defect with sites | `BDS.Comm.DE.25 Encephalocele` | `List – select one` |
| a site | `BDS.Comm.DE.28 Occipital encephalocele` | `List value` |

The kit says which list each row belongs to in a column of its own, `List to include this data
element in`, which its READ ME describes as indicating "if the data element is part of a list of
data elements", giving anencephaly and craniorachischisis as its example.

A row in the middle of that tree is therefore **both a question and one of the values of the
question above it**. Carried only as a question, the mandatory top of the tree has no values at
all and degrades to a free-text box; carried only as a value, the eight encephalocele sites have
no question to sit on. So it is recorded as both, and each level is gated on the value above it:
picking `Central nervous system defects` reveals that question, picking `Encephalocele` reveals
its eight sites. Twenty-seven of the anomaly form's thirty-two questions are gated this way.

The gate is exact rather than inferred — the value is the very string the child was appended to
its parent's list as, so it cannot fail to match. Ungated, a case with one anomaly would be shown
all ten body-system groups and every sub-list beneath them at once, and a `Select all that apply`
with no gate says all of them are being asked.

### The parent is named, not positional

The SRV kit has the same column and the reader ignored it, parenting each option to the row above
it instead, because that kit paraphrases or misspells the parent on 13 of its rows. That reading
cannot survive a nested value set: the row above an option is often a sibling list rather than its
parent. `BDS.Comm.DE.45 Microcephaly` follows the last of the ten spina bifida values and belongs
to `Central nervous system defects` two levels up; read positionally it becomes an eleventh kind
of spina bifida. `BDS.Comm.DE.64 Robin sequence` is the same, under `Orofacial defects`.

So the named list wins where it resolves to a list already read on the tab, and the row order is
the fallback where it does not. Both fallbacks are load-bearing:

- 14 of this kit's option rows name no list at all — the values of `Case record status`,
  `Congenital anomaly diagnosis status`, `Congenital anomaly clinical presentation` and
  `Congenital anomaly coding: laterality`, which are flat lists at the top of the tab.
- This kit also uses the same column for a **functional grouping**. `Newborn death` heads a date
  of death, a cause, an autopsy flag and its details, and is a `Boolean` rather than a list, so
  the five rows naming it resolve to nothing and stay where the row order put them.
- The SRV kit's three rows naming an `Admission type` it never defines resolve to nothing, which
  is why that kit's output is unchanged by the rule.

## Three processes, two forms

The kit has three business processes, and **no data element belongs to the second of them
alone**. All 152 rows of `BDS.Common` and all 105 of the collection tab name activities of process
A *and* of process B in one cell, because case confirmation re-opens the same case record rather
than collecting anything new. A survey per process would build the second one out of the first
one's questions and drop every one of them as a repeated code, `pde-<code>` being a global key.

What the kit does divide on is grain:

| Grain | Where | Carried? |
|---|---|---|
| **The case** — the newborn, the pregnancy, the parents, collected or abstracted from the record | `BDS.A.Data collect abstract` | yes |
| **The anomaly** — what the defect is, how it presents, whether the diagnosis is confirmed | `BDS.Common` | yes |
| **The review** — what the specialist and the data manager send back about a recorded case | `BDS.B.Case confirmation` | yes |
| **The periodic report** — whether a generated report is satisfactory, and its approval | `BDS.C.Data aggregation` | no |

`BDS.C` is in no survey. Its four elements are about a report over many cases rather than about a
case, and a form asking for them would collect a judgement on data the deployment already holds.
That is the same grain the SRV kit reports upward and the same reason it is left out; what those
elements state is what a `metric__` layer computes.

The activity slice still earns its place. Every row of `BDS.Common` names four or five activities
in one cell, so without it the whole cell becomes the screen title; naming the A-process
activities takes each row under the one it was collected at.

## What the patient record keeps

Seven elements of the collection tab are not on any form, because Tamanu already holds them: the
newborn's first name, last name, unique ID, date of birth, whether that date is unknown, sex, and
the health facility ID. A DAK registers its own client because it cannot assume a record exists;
collecting these onto a form as well would give a deployment two places to write one fact and no
rule for which counts.

The parents' names and identifiers are **kept on the form** deliberately. Tamanu links a patient
to a mother and a father through `patient_additional_data`, but the link exists only where both
are patients of this deployment, and a surveillance case is routinely recorded for a newborn whose
mother is not — so dropping them would lose the fact rather than move it.

The mother's two addresses are kept for a different reason: `Mother's primary early pregnancy
residential address` and `Mother's primary residential address at time of delivery` are historical
and specific to where an exposure may have occurred, and are not the current address a patient
record holds.

## The selection rule

An element is carried when it is `Required = R`, or feeds an Annex C indicator, or is named in the
kit's core shortlist. This kit leans on the third rule harder than most, in three places.

### The tree's middle and lower levels

A list nested inside another list carries no `Optionality` of its own — the kit flags the top of
the tree `R` and leaves every level beneath it blank — and links an indicator only on the ten
body-system groups. The seventeen sub-lists below them are named by an indicator rather than
linked from one: `BDS.IND.4` counts `"Congenital anomaly diagnosis" included in "Encephalocele"
list`. Without the sub-list there is a tick for `Encephalocele` and no way to say which of the
eight sites it was, and the indicator counting it has nothing to count.

### Consent

The kit gives consent two of the collection process's five activities and marks all four elements
`C`, "required if demanded by the surveillance system" — a statement about the deployment's rules
rather than about an answer given earlier, which is the one thing the `Optionality` flag cannot
say. Left to the first two rules the whole of both activities drops, and the form asks for a
photograph of a newborn without recording the consent taken for it.

### The pregnancy, the birth and the death

Gestational age and its unknown flag, the three measurements, the newborn's death and its cause,
and parental consanguinity are each `C` or `O` and named by no indicator. Each is what a birth
defects prevalence is stratified by, or — for consanguinity — the aetiology a registry exists to
detect.

### The whole of the case-confirmation process

`BDS.B`'s four elements are all `O` and linked to no indicator, and between them are the entire
record of what the birth defects specialist and the data manager did with a case.
`Diagnosis correction` is the one the kit's own `BDS.IND.42` counts — `COUNT of birth defects
cases with "Diagnosis correction" = FALSE` — while leaving its indicator-linkage column blank, so
the linkage rule cannot see it and the accuracy indicator would have no numerator.

## What the reader had to learn

Four rules of the reader are this kit's.

### List types written with an en dash

`List – select one` and `List – select all that apply`, where the SRV kit writes the same two
types with a hyphen. The separator is now levelled before the type lookup rather than every dash
spelling being named. Unmatched, `List – select one` is not `Coding`, the row never becomes a
parent, and the whole anomaly tree imports as free text.

### The parent is named

See § The parent is named, not positional above.

### `Activity ID and name` in one column under that name

Every other kit heads the column `Activity ID`, whether it holds the id alone or the id and the
name together; the SRV kit gives them a column each. This one heads a single column with both
names at once.

### `Signature` and `Attachment` data types

Neither appears in any other kit. Tamanu has a question type for each — `Signature`, and `Photo`
for the attachment, which is the only type that stores a file and is what this kit's own legend
gives as the `Attachment` example. Unmapped, both fall through to free text, and a consent
signature captured as typed text is not a signature.

Two console reports were also reading the crosswalk's raw type, which for a kit stating the choice
in the data type is never the canonical `Coding`, so every coded element of this kit and of the
SRV kit was silently exempt from both. They now normalise the type first, which is what surfaces
the four country-configured elements below.

## Dictionary defects carried as found

### Four coded elements with no value set

`BDS.A4.DE.3 [Administrative area]`, `BDS.A12.DE.35 Cause of death`, `BDS.A12.DE.85 Mother's race`
and `BDS.A12.DE.86 Mother's ethnicity` are typed as lists and given no values. These are
country-configured by design — the administrative area is a placeholder in brackets, and race and
ethnicity categories are national — so they are emitted as free text rather than given a list this
repository invented. A deployment supplies its own.

### Five indicator values that match no option string

Annex C writes five of its values differently from Annex A, and the coverage check reports each
rather than passing it:

| Annex C writes | Annex A defines |
|---|---|
| `Triscupsid valve atresia` | `Tricuspid valve atresia` |
| `Interuppted aortic arch` | `Interrupted aortic arch` |
| `Congenital rubella syndrome (CRS)` | `Congenital rubella syndrome` |
| `Congenital cytomegalovirus (cCMV)` | `Congenital cytomegalovirus` |
| `Congenital Zika syndrome (CZS)` | `Congenital Zika syndrome` |

Two are misspellings and three add an abbreviation the dictionary does not carry. The forms use
the dictionary's spelling, because that is the string a health worker picks and the string that
lands in `survey_response_answers.body`. An indicator quoting one of these needs the dictionary's
spelling on its side of the comparison.

`Tranverse terminal limb deficiency` is missing an `s` in both annexes, so it is not in this list:
it is carried as the kit spells it, and the two sides agree.

### A functional grouping in the list column

`Newborn death` names a group of five elements rather than a value set, in the column that
otherwise names a parent list. It is a `Boolean` rather than a list, so it resolves to nothing and
the five rows stay where the row order put them. See § The parent is named, not positional.

## No decision-support logic

The kit publishes no Annex B. Its `input/decision-logic/` directory at the released tag holds
nothing but the `.gitignore` that would have hidden the workbook, and the implementation guide's
own decision-logic page is empty.

So `DECISION_SUPPORT` is empty and no form carries a guidance prompt or a patient issue. Nothing
is invented to fill the gap: a prompt this repository authored would be a clinical recommendation
WHO has not made.

## Annex C coverage

All 42 indicators are computable from these forms. Check it against the current spec with:

```bash
cd forms/who-dak
python annex_c_coverage.py --domain bds
```

Every prevalence indicator has the same shape — a count of cases whose `Congenital anomaly
diagnosis status` is `Confirmed diagnosis` and whose `Case record status` is `Complete`, with a
particular anomaly, over the births in the surveillance population. The denominator is not a form
question in any of them: it is the total births in the catchment, which comes from the deployment's
own denominator source rather than from this program.

`BDS.IND.39` counts non-missing optional elements per case record, which is a property of the
submitted form rather than an answer on it, and `BDS.IND.43` subtracts the date of birth from the
date of completion. Both are `metric__` layer calculations over the responses.

## What cannot be encoded

| DAK content | Why not |
|---|---|
| The denominators — total births, live births, male births in the surveillance population | Not a fact about the case in front of the data collector. A deployment supplies them from its own birth records. |
| `BDS.C` data aggregation | About a periodic report over many cases. See § Three processes, two forms. |
| Annex D functional and non-functional requirements | A conformance checklist for the deployment, not form content. |
| The `Explain conditionality` prose on 26 elements | Stated as narrative — "required if surveillance is facility-based" — rather than as a rule over answers. Only the `Other (specify)` pattern is gated mechanically, alongside the value-set nesting. |

## Fetching the components

The annexes are not committed. Each is fetched from the pinned tag; the generator prints the
command when Annex A is absent, and `domain.py` records the sha256 so a WHO revision announces
itself rather than quietly changing a form.

```bash
mkdir -p forms/who-dak/bds/annexes
curl -sL -o "forms/who-dak/bds/annexes/BDS DAK_core data dictionary.xlsx" \
    "https://raw.githubusercontent.com/WorldHealthOrganization/smart-dak-bds/v1.0.0/input/dictionary/BDS%20DAK_core%20data%20dictionary.xlsx"
curl -sL -o "forms/who-dak/bds/annexes/BDS DAK_indicators.xlsx" \
    "https://raw.githubusercontent.com/WorldHealthOrganization/smart-dak-bds/v1.0.0/input/indicators/BDS%20DAK_indicators.xlsx"
```

There is no Annex B to fetch.
