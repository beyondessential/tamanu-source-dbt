# DAK conformance — family planning

What these forms take from the WHO DAK for family planning, what they deliberately do differently,
and what the DAK specifies that a Tamanu form cannot hold.

## Source

Everything is generated by [`../dak_generator.py`](../dak_generator.py) from **Web Annex A**, the
kit's core data dictionary (`WHO-SRH-21.13-eng.xlsx`, 641 data rows across four `FP.*` tabs, 121 of
them parent elements). Annex A gives each data element an ID (`FP.B.DE257`), a label, a data type, a
`Required` flag, terminology codes (ICD-11 / ICD-10 / LOINC / ICHI / ICF / SNOMED CT) and — for
coded elements — one child row per input option (`Multiple Choice Type = "Input Option"`).

Eleven further rows come from **Web Annex B**, the decision-support logic. Nothing is authored by
hand.

## What the forms are

Four surveys, one per DAK business process: 78 questions from the dictionary plus 8 guidance
prompts and 3 patient issues, over 24 screens.

| | |
|---|---|
| Questions answerable in the form | 81 |
| — of which carry a data element id | 77 |
| — of which the dictionary never numbered | 1 (`Current medications`) |
| — of which are decision-support issues | 3 |
| Coded questions carrying the kit's options | 23 (426 options; 1 repeat dropped) |
| Mandatory | 41 — exactly the kit's `Required = R` |
| Linked to an Annex C indicator | 3 |
| Label / option / mandatory mismatches against the dictionary | 0, verified on every build |

- **Question codes** carry the data element id: `FP.B.DE257` → `whodakfp-b-de257`, `FP.C.DE17` →
  `whodakfp-c-de17`.
- **Labels and option strings** are Annex A's, verbatim. Option strings are what land in
  `survey_response_answers.body`, so nothing downstream can compensate for strings that do not match
  the dictionary.
- **The option string comes from the `Input Options` column**, falling back to the option row's own
  label where that column is empty, `N/A`, or names another option of the same question. This kit
  populates both and they differ for 62 of its 471 option rows.
- **Screens are the DAK's own activities**, and within an activity the kit's category dividers
  become section headings.
- **`FP.D. Referral` is Tamanu's `referral` survey type**, so it lands on the facility Referrals
  tab; the rest are `programs`.
- **All four tabs become forms.** This kit publishes no configuration tab, where the ANC and PNC
  kits each hold one back.
- Each question carries a `_dak` block in the spec — data element id, activity, data type, why it
  was selected, and its indicator links. That is the crosswalk source, and is not written to the
  workbook, which has no column for it.

### The selection rule

Annex A's four tabs hold 121 parent elements. An element is included when it is:

1. `Required = R` — the DAK says a system must capture it;
2. linked to an Annex C indicator — it feeds something reported;
3. named in the domain's shortlist.

That yields 78. **Rules 1 and 2 do far less work here than in any other kit read so far**: only 41
elements are `Required = R`, and Annex A links just three of the whole dictionary to an indicator,
against 15 for the ANC kit and 140 indicators' worth for the HIV one. Rules 1 and 2 alone select
nine questions on `FP.A`, 18 on `FP.B`, five on `FP.C` and ten on `FP.D`.

Five on `FP.C. Service provision` is the problem the shortlist exists to fix. The tab's five
`Required = R` elements are *method or service provided*, *provider*, *service provision date*,
*back-up method needed* and *follow-up recommended* — the record of what was handed over. Every
element of the pregnancy checklist is `Required = C`, so without the shortlist the form records a
hormonal method being started or an IUD inserted with no record that pregnancy was excluded first,
which is the safety gate the kit puts a whole decision table (`FP.DT.10`) and a whole activity
(`FP.C3`) behind.

The shortlist adds 36 elements over the two clinical tabs. Every entry is one of:

| Why it is in the shortlist | Elements |
|---|---|
| An Annex C calculation names it, but Annex A links no element to that indicator | `FP.B.DE12` (`FP.IND.5`), `FP.B.DE105` (`FP.IND.4`), `FP.B.DE42` (`FP.IND.7`), `FP.B.DE33` / `FP.B.DE34` (`FP.IND.8`) |
| An encoded Annex B rule reads it | `FP.B.DE35`, `FP.B.DE47`, `FP.B.DE50` (`FP.DT.10`); `FP.B.DE133`, `FP.B.DE134`, `FP.B.DE148` (`FP.DT.03`) |
| The pregnancy checklist and its conclusion | `FP.C.DE1`–`FP.C.DE9`, `FP.C.DE12` |
| A branch the care pathway turns on | `FP.B.DE209`, `FP.B.DE213`, `FP.B.DE214` |
| Why the client left without the method they chose | `FP.B.DE83`, `FP.C.DE47`, `FP.C.DE54`, `FP.C.DE62` |
| When the method the client arrived on was administered, which `FP.S.1` counts from | `FP.B.DE79`–`FP.B.DE82` |
| The counselling entry point, and the follow-up date the schedule is expressed against | `FP.B.DE16`, `FP.B.DE28`, `FP.B.DE149`, `FP.C.DE68` |

## Deliberate divergence

| What | Where | Why |
|---|---|---|
| A heading inside an option list does not close the parent | `read_annex_a` in [`../dak_generator.py`](../dak_generator.py) | This kit groups a single element's options with the same untyped heading rows the PNC kit uses to break up a tab. `FP.B.DE257 Health condition(s)` carries 154 options under 21 of them (*Diabetes*, *Hypertension*, *Liver disorders*) and `FP.B.DE149 Issues and concerns` 54 under ten. Closing the parent at each heading orphaned every option past the first, leaving two `Required = R` and `Required = C` Select-alls as free-text boxes. What separates the two cases is the row that follows: an option row means the list is still open, a typed element means the heading introduces a section. Tamanu has no option-group construct, so the grouping itself is dropped and the run reports each heading — it is instead the source of the registry's condition classes |
| A row repeating the label above it is a continuation, not a heading | `read_annex_a` in [`../dak_generator.py`](../dak_generator.py) | `FP.A.DE11 Age (coded to ICD groupings)` is spread over five rows so that five ICD-11 age bands — *Early Adolescence*, *Middle Adolescence*, *Late Adolescence*, *Young Adult*, *Adult* — each get a row of their own. The four after the first hold a terminology code and nothing else. Read as headings they left a section called "Age (coded to ICD groupings)" standing over `Sex`, the next question the selection rule keeps |
| `Current medications` gets a code built from its activity and label | `question_code` in [`../dak_generator.py`](../dak_generator.py) | The dictionary numbers `FP.B.DE241` and then `FP.B.DE242`, and puts a `Required = R` `Coding` element owning fourteen option rows between them with no id at all. `whodakfp-` is not a code, and no DAK id is invented for it: the code is `whodakfp-b11-4-current-medications`, `_dak.dataElementId` is left blank, and the run reports it. Dropping the element instead would lose the antiretroviral, anticonvulsant and rifampicin options, all of which change a client's medical eligibility |
| An `Input Options` cell naming another option of the same question falls back to the row's label | `resolve_option_strings` in [`../dak_generator.py`](../dak_generator.py) | `FP.B.DE452`'s third option row is labelled *Home/self-administered* but its `Input Options` cell reads "Referral", the option directly above it. Carried as written, the two collapse to one and a `Required = R` question loses the answer that a method was self-administered — which for DMPA-SC is a WHO-recommended self-care intervention, not an edge case. The row's own label is the other string the dictionary gives that row, so nothing is invented |
| `FP.B.DE35 Breastfeeding` is typed `Coding` via `ELEMENT_TYPES` | [`domain.py`](domain.py) | Typed `Boolean` with `Input Options` of "Yes/No", then followed by five `Input Option` rows giving breastfeeding *intensity* — exclusive, fully, nearly fully, partially. Annex B settles which the kit means: every row of `FP.DT.10`'s pregnancy checklist reads `"Breastfeeding status" = "Fully breastfeeding" OR "Nearly fully breastfeeding"`, comparing the element against the option strings listed under it. Read as a Boolean the five options had no parent and were dropped, and LAM eligibility became unrecordable |
| The four `FP.B` rows with prose in the `Required` column are not carried | `selected` in [`../dak_generator.py`](../dak_generator.py) | Three say so explicitly — `FP.B.DE412 Sexual violence` is marked *"this data element should not be recorded or retained in the health record"*, and `FP.B.DE413` / `FP.B.DE418` *"only used for outputs in the decision support logic"* — and `FP.B.DE423 Client preferences` has a bare `0`. None is `R` and none feeds an indicator, so the selection rule drops all four without a special case. Carrying `DE412` would be worse than a defect: the kit is telling implementers not to store it |
| The nine `Codes` rows under `FP.B.DE413` and `FP.B.DE418` are not carried | `selected` in [`../dak_generator.py`](../dak_generator.py) | Labelled *1*, *2*, *3*, *4*, *Accept*, *Caution*, *Delay*, *Special* — the MEC categories and their actions. They are option rows the dictionary marks `N/A` rather than `Input Option`, so they read as elements, and their `Required` column is blank. Their two parents are decision-support outputs the kit says not to collect, so all eleven rows fall away together |
| `Select One` is read as a single-select | `tamanu_type` in [`../dak_generator.py`](../dak_generator.py) | `FP.C.DE44` is the only row in any kit read here to capitalise the *O*. It is typed `Coding`, which is what makes a row an option parent, so the spelling costs nothing — but a kit that wrote `Select One` on a row it left untyped would lose its options, and the multiple-choice-parent set is matched case-sensitively |

## Decision support (Annex B)

### What is encoded

Eight guidance prompts and three patient issues, from four of the kit's 28 decision tables. Each
shows the annexe's own guidance when its inputs are answered, and leaves the judgement with the
clinician.

| Rule | Survey | Fires on | What it says |
|---|---|---|---|
| `FP.DT.01` | `counselling` | `Reason for follow-up` = *Issues and concerns / method failure* | A returning client with a problem needs the most time |
| `FP.DT.01` | `counselling` | `Reason for follow-up` = *Contraceptive continuation* | A routine resupply needs little counselling |
| `FP.DT.03` ×3 | `counselling` | Any of twelve `STI risk assessment factors` | Counsel on dual protection; raises a patient warning |
| `FP.DT.06` | `counselling` | `Method in mind` = *Yes* | Check the client's understanding is accurate |
| `FP.DT.06` | `counselling` | `Method in mind` = *No* | A new client with no method in mind needs the longest consultation |
| `FP.DT.10` | `serviceprovision` | `Reasonably certain a woman is not pregnant` = *No* | Test before starting a hormonal method or inserting an IUD |

`FP.DT.03` is three prompts rather than one because a gate naming all twelve factors serialises to
430 characters against a varchar(255) `visibility_criteria` column. They are split where the list
crosses the limit rather than on any clinical grouping — Annex B draws no distinction between the
factors, and dropping factors to fit is not an option when the point of the rule is that any one of
them raises the client's risk. A client with factors from more than one part sees more than one
prompt, which is the right failure. Annex A's thirteenth option, *No risk factors*, is
deliberately not gated on: it is the answer that means the rule does not apply.

`FP.DT.01`'s third input is `"Reason for follow-up" = "Method switch"`, which Annex A does not offer
as an option of that element. A gate naming it would never fire, so the generator refuses it rather
than emitting guidance that silently never appears.

### What is not encoded

- **The medical eligibility criteria — twelve of the 28 tables.** `FP.DT.08.1` through
  `FP.DT.08.12` are the WHO MEC wheel, one table per method family, each mapping a client's
  conditions and medications onto a category 1 to 4 for that method. They run to 205–245 rows
  apiece and evaluate as a matrix, not a rule: a form has no way to score 154 conditions against 12
  methods and return a category. The forms collect both inputs — `Health condition(s)` and
  `Current medications` — and the registry carries the conditions between contacts so the clinician
  is reading a history rather than one contact's answers.
- **`FP.DT.02` HEADSS assessment** fires on age under 19. Age lives on the patient record, not on
  a form, so a form-level gate cannot see it.
- **`FP.DT.04` IPV assessment** fires on `"Minimum requirements for IPV assessment" = TRUE`, which
  is a property of the *facility* — private space, a trained provider, a referral pathway — not of
  the client. It is not an Annex A element on any of these four tabs.
- **`FP.DT.05` Issues and concerns**, 162 rows of side-effect management keyed on the client's
  current method crossed with the issue reported. A prompt would have to name a method-and-issue
  pair per row; the form records the issue and leaves the management to the clinician.
- **`FP.DT.09` Where services can be provided** reads `"Stock available"` and `"Health worker is
  skilled to provide"`. Both are facts about the site at that moment, and neither is an Annex A
  element.
- **`FP.DT.10`'s positive branch.** The kit concludes pregnancy can be excluded when *any one* of
  seven checklist questions is answered yes. A Tamanu `visibilityCriteria` spanning several
  questions is a conjunction, so the disjunction cannot be expressed. What is encoded is the branch
  with a clinical consequence — the checklist having failed.
- **`FP.DT.12` When to start** and **`FP.DT.13` Back-up method**, 165 and 149 rows keyed on method
  crossed with where the client is in her cycle. Same shape as the MEC tables and the same reason.
- **`FP.DT.14` and `FP.S.1`, the follow-up schedule.** Both compute a date from the method given —
  `"Service provision date" + 84 days` for an injectable, `+ 7 days` for female sterilization. A
  form cannot write a date into another field, and Tamanu's own scheduling is not a survey
  construct. `FP.C.DE68 Recommended follow-up date` is carried so the date can be recorded, and the
  registry's loss-to-follow-up threshold is drawn from this table.

## Annex D

Not encodable in a form, and not attempted: `WHO-SRH-21.16-eng.xlsx` is 33 functional and 69
non-functional requirements about the *system* — password-protected access, confidentiality of the
record, anonymised export, the ability to bypass the standard flow for an urgent case. They are a
checklist for a deployment's Tamanu configuration and infrastructure, not content for a survey.

## Known gaps, in priority order

1. **`Current medications` imports as a mandatory single-select.** The dictionary types it `Coding`
   but never fills in the multiple-choice column, and the generator does not guess — the same
   handling the HIV and ANC kits get for two elements each. Here it matters more: the element is
   `Required = R`, its fourteen options are drug classes that change medical eligibility, and a
   client on antiretrovirals *and* rifampicin can record only one. A deployment should switch it to
   `MultiSelect` before first import.
2. **`FP Registration` duplicates the Tamanu patient record.** Unique identification, first name,
   last name, address, sex and mobile phone number as survey questions are the anti-pattern Tamanu
   forms exist to avoid, and all six are `Required = R` so the selection rule cannot leave them out.
   Six of the nine questions on that form are already on the patient record; only `Visit date`,
   `Referral` and `[Administrative Area]` are not. A deployment should reduce the demographic
   questions to `PatientData` reads.
3. **`Mobile phone number` and `Provider's telephone number` are `Number` questions**, because the
   dictionary types them `Quantity`. A leading zero or a `+` country code cannot be stored. The
   type is Annex A's and is left alone; a deployment wanting to keep the field should make it free
   text.
4. **`Health condition(s)` is a single question with 154 options.** That is what the dictionary
   says and what the MEC needs, but it is not a list a health worker scrolls at the bedside. The 22
   groups the kit divides it into are carried as the registry's condition classes rather than lost,
   and a deployment may prefer to split the question along the same lines.
5. **Two coded elements have no option list**, so they import as free text: `FP.A.DE2
   [Administrative Area]` and `FP.C.DE44 Provider that served the client`. Both are
   country-configured by design — the kit expects a local list — and neither should stay free text
   in a real deployment.
6. **Conditional visibility is almost absent.** The dictionary expresses conditionality as prose in
   `Skip Logic` plus a `Required = C` flag, which does not translate mechanically into
   `visibilityCriteria`. The eleven Annex B rows are the only gated content — this kit's selection
   carries no "Other (specify)" free-text box — so each form asks nearly every one of its questions
   every time. It matters most on
   `FP.C`, where the pregnancy checklist and the pregnancy test are alternatives rather than a
   sequence, and on `FP.B`, where the four *date method administered* questions all show whether or
   not the client arrived on a method.

## Indicator coverage

`python annex_c_coverage.py --domain fp` reads Annex C's own calculations, which this kit writes in
terms of quoted Annex A labels, and compares them against the generated forms:

| | |
|---|---|
| Indicators in Annex C | 8 |
| Computable from the forms | **4** — `FP.IND.1`, `FP.IND.2`, `FP.IND.3`, `FP.IND.6` |
| Gap | 4 — `FP.IND.4`, `FP.IND.5`, `FP.IND.7`, `FP.IND.8` |
| No computable numerator — Annex C's own statement | 0 |

All four gaps are the same defect, and none is a missing question: **Annex C names an element that
Annex A does not define.** `FP.IND.4` counts `"Contraceptive method switch"`, `FP.IND.5`
`"Stopping contraception"`, `FP.IND.7` `"Recent miscarriage or abortion"` and `FP.IND.8`
`"Time postpartum ≤ 365.25 days"` — four labels that appear nowhere in the data dictionary. Each
has a near-equivalent that *is* on the forms, put there by the shortlist for exactly this reason:
`Method at intake` with `Chosen method` and `Methods previously used` give a switch;
`Reason for stopping contraception or method` gives a discontinuation;
`Miscarriage or abortion within past 4 weeks` and `Time since delivery` give the other two.

So all eight are computable in practice, and four of them need a `metric__` model to bridge the
naming rather than a change to these forms. That bridge is the right place for it: widening the
selection would not help, and loosening the comparison in `annex_c_coverage.py` would turn a real
finding into a green tick.

Reading these counts as coverage of the family planning programme would be wrong in the other
direction, too. Annex C disaggregates every one of its eight indicators by age band, method and
service site, and `FP.IND.1`'s numerator also asks for clients who "have not used contraception in
6 months" — a history question no single contact's form can answer.

## Terminology linkage

Annex A carries ICD-11, ICD-10, LOINC, ICHI, ICF and SNOMED CT codes per element, and the generator
reads none of them into the spec: Tamanu's `program_data_elements` has no column for a terminology
code, and a question's `code` is the DAK id. The crosswalk is the `_dak.dataElementId` in the JSON
spec, which maps a Tamanu question back to the row that carries every code the kit assigns.

`FP.A.DE11 Age (coded to ICD groupings)` is the one element where the codes change what the reader
does rather than what it stores: the kit gives it five ICD-11 age-band codes across five rows, and
those four extra rows are read as continuations of it. See § Deliberate divergence.

## Fetching the annexes

The annexes are not committed — third-party spreadsheets WHO serves at stable IRIS URLs, ignored via
`<domain>/annexes/`. [`domain.py`](domain.py) records the IRIS handle and the DSpace bitstream URL
for each, and the sha256 of Annex A, which `dak_generator.py` verifies and warns about on mismatch
— so a revised annexe announces itself rather than quietly changing a form.

```bash
mkdir -p forms/who-dak/fp/annexes
cd forms/who-dak/fp/annexes
curl -sL -o WHO-SRH-21.13-eng.xlsx \
    https://iris.who.int/server/api/core/bitstreams/406d65f8-7a8a-49dc-ad11-2c5ea805c7cb/content
curl -sL -o WHO-SRH-21.14-eng.xlsx \
    https://iris.who.int/server/api/core/bitstreams/ea37207e-aeed-4675-b1c3-94e76aa0ba25/content
curl -sL -o WHO-SRH-21.15-eng.xlsx \
    https://iris.who.int/server/api/core/bitstreams/ac9db106-a2d2-4ac4-8c51-628b366ab8b6/content
curl -sL -o WHO-SRH-21.16-eng.xlsx \
    https://iris.who.int/server/api/core/bitstreams/93aebec4-1089-4267-a464-8e56c7aa4a28/content
```

The four annexes are separate IRIS items under handles `10665/341998` through `10665/342001`, all
children of the publication at
[9789240029743](https://www.who.int/publications/i/item/9789240029743). The bitstream URLs above
are what those handles resolve to; the older `apps.who.int/iris/bitstream/handle/...` form still
redirects to them.

## Rebuilding

```bash
cd forms/who-dak
FORMS_SKILL=../../../claude-plugins/plugins/tamanu/skills/build-tamanu-forms/scripts
python dak_generator.py --domain fp
python $FORMS_SKILL/build_program_xlsx.py \
    --spec fp/who-dak-fp_program.json --out fp/who-dak-fp_program.xlsx
python annex_c_coverage.py --domain fp
```

The generator reports every dictionary defect it absorbed — the 32 option-group headings it
swallowed, the four ICD continuation rows, the unnumbered element, the relabelled option, the
repeated option and the two country-configured elements. A run that reports something new means the
annexe changed, and the checksum warning will have said so first.
