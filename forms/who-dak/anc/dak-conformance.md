# DAK conformance — antenatal care

What these forms take from the WHO DAK for antenatal care, what they deliberately do differently,
and what the DAK specifies that a Tamanu form cannot hold.

## Source

Everything is generated by [`../dak_generator.py`](../dak_generator.py) from **Web Annex A**, the
kit's core data dictionary (`WHO-SRH-21.1-eng.xlsx`, 1,083 data rows across 10 `ANC.*` tabs). Annex A
gives each data element an ID (`ANC.B9.DE34`), a label, a data type, a `Required` flag, terminology
codes (ICD-11 / ICD-10 / LOINC / ICHI / ICF / SNOMED CT) and — for coded elements — one child row
per input option (`Multiple Choice Type = "Input Option"`).

Six further prompts come from **Web Annex B**, the decision-support logic. Nothing is authored by
hand.

## What the forms are

Nine surveys, one per DAK business process: 152 questions from the dictionary plus 6
decision-support prompts, over 17 screens.

| | |
|---|---|
| Questions carrying a DAK data element id | 152 of 152 |
| Coded questions carrying Annex A's options | 33 of 33 (246 options) |
| Mandatory | 138 — exactly the DAK's `Required = R` |
| Linked to an Annex C indicator | 15 |
| Label / option / mandatory mismatches against the dictionary | 0, verified on every build |

- **Question codes** carry the DAK id: `ANC.B9.DE34` → `whodakanc-b9-de34`, `ANC.End.1` →
  `whodakanc-end-1`.
- **Labels and option strings** are Annex A's, verbatim. Option strings are what land in
  `survey_response_answers.body`, so nothing downstream can compensate for strings that do not match
  the dictionary.
- **The option string comes from the `Input Options` column**, not from the option row's own label.
  This kit populates both and they differ for 196 of its 660 option rows: `ANC.B5.DE19` is labelled
  *Fluid loss (leaking)* but offers *Fluid loss*, and the three `ANC.B6.DE28`–`DE30` rows labelled
  *Last live birth was preterm* / *…was not preterm* / *Don't know…* offer *Yes* / *No* / *Does not
  know*. The label is the element's name; the `Input Options` cell is what a health worker picks.
- **Screens are the DAK's own activities**, and within an activity the kit's category dividers
  become section headings. That sub-structure matters here in a way it does not for the HIV kit:
  `ANC.B9` puts all ninety of its elements under one activity, and its *Ultrasound scan* and *HIV
  test* dividers are the only grouping it has.
- **`ANC.C. Referral` is Tamanu's `referral` survey type**, so it lands on the facility Referrals
  tab; the rest are `programs`.
- Each question carries a `_dak` block in the spec — data element id, activity, data type, why it
  was selected, and its indicator links. That is the crosswalk source, and is not written to the
  workbook, which has no column for it.

### The selection rule

Annex A's nine form-bearing tabs hold 351 parent elements. An element is included when it is:

1. `Required = R` — the DAK says a system must capture it;
2. linked to an Annex C indicator — it feeds something reported;
3. named in the kit's core shortlist.

That yields 152. Rule 3 is nearly unused, because this kit *is* the core list: the Overview sheet
titles Annex A "Web Annex A: Core data dictionary", and there is no Component 5 shortlist to consult
the way the HIV kit has one.

It is used for one tab. `ANC.End` records how the pregnancy ended, and only the closure reason, the
delivery date and the place of delivery are `Required = R`; delivery mode, birth weight, delivery
complications, the date of a miscarriage or death and the cause of death are all `Required = C` with
no indicator link. Rules 1 and 2 therefore produce a form that records *that* a woman delivered
without recording *how*, and leave the registry's own closure statuses — which are this tab's
`ANC.End.1` options — standing over nothing. The eight outcome elements are named in
[`domain.py`](domain.py).

## Deliberate divergence

| What | Where | Why |
|---|---|---|
| Seven `ANC.B9` test elements are typed `Boolean` against the dictionary | `ELEMENT_TYPES` in [`domain.py`](domain.py) | Every `<test> required` / `<test> ordered` / `<test> conducted` triplet in the tab is Boolean, except these seven, which the kit leaves untyped or types `Coding` with no input options. Either lands as a free-text box in the middle of a column of yes-no questions, and four of them are `Required = R`, so it lands as a *mandatory* one. The type is read off the sibling rows, not invented |
| `ANC.Configuration` becomes no form | `PROCESSES` in [`domain.py`](domain.py) | Site constants — malaria and HIV prevalence in the population, whether ultrasound and each test is available here. One value per site, read by the decision logic; settings or a seed, not a survey |
| One coded element is emitted as free text | generated, reported by the run | `ANC.B7.DE1 Medication follow-up` is `Coding` with no input options in the dictionary. A list is not invented for it; supply a local coded list or an `Autocomplete` over existing reference data |
| Two coded elements are emitted as single-select | generated, reported by the run | `ANC.B8.DE117` and `ANC.B10.DE210` are `Coding` with the multiple-choice column left blank, so the dictionary does not say whether more than one answer is allowed. `Radio` is the narrower reading and is reported rather than assumed silently; `ANC.B8.DE117` is indicator-linked and its label says *types*, plural, so it is the likelier of the two to want `MultiSelect` |
| Heading codes name the heading, not its position | `heading_code` in [`../dak_generator.py`](../dak_generator.py) | An activity heading takes the DAK's own activity id — `ANC.B10.1` becomes `whodakanc-counselling-act-b10-1` — and a section heading, which no kit gives an id, takes its own text. A code built from a running question index moves whenever a question is inserted ahead of it, upserting a new row and stranding the old one. Where a kit gives two different activities the same id, the later takes a numeric suffix and the run reports it |
| Category dividers become `Instruction` headings | `read_annex_a` in [`../dak_generator.py`](../dak_generator.py) | A row the dictionary gives no data type, no multiple-choice type and no `Required` flag is a section heading, whether or not it carries an id — `ANC.B9.DE32 "HIV test"` heads the three HIV-test elements after it. A heading with no selected element under it is dropped |
| `ANC.B6.DE14` appears twice on its tab | `read_annex_a` in [`../dak_generator.py`](../dak_generator.py) | One row is the *Gestational age* section heading, the other the real *Last menstrual period (LMP) date* element. The typed row wins, rather than row order deciding |

## Decision support (Annex B)

### What is encoded

| Rule | Survey | Fires on | Effect |
|---|---|---|---|
| `ANC.DT.01` | Quick Check | any of the thirteen danger signs on `ANC.B5.DE48` | Guidance to refer urgently, plus a Tamanu patient issue |
| `ANC.DT.04` | Physical Examination | systolic ≥ 140 on `ANC.B8.DE17` | Guidance to rest the woman and measure again |
| `ANC.DT.04` | Physical Examination | diastolic ≥ 90 on `ANC.B8.DE19` | Guidance to rest the woman and measure again |

Two mechanical splits, both forced by Tamanu rather than by clinical judgement:

- **`ANC.DT.01` is emitted as two prompts.** A gate naming all thirteen danger signs serialises to
  275 characters and `survey_screen_components.visibility_criteria` is varchar(255). Dropping signs
  to fit is not an option when the point of the rule is that any one of them is urgent, so the list
  is split where it crosses the limit and both halves carry the same guidance. A woman with signs
  from both halves sees both prompts, which is the right failure.
- **`ANC.DT.04` is emitted as two prompts.** Annex B raises on systolic ≥ 140 *or* diastolic ≥ 90,
  and a `visibilityCriteria` spanning two questions is a conjunction, so each measurement carries
  its own prompt.

Each range gate names a ceiling no sphygmomanometer reports rather than one at the edge of the
plausible range: a range gate stops firing above its end, and the reading that most needs the prompt
is the extreme one.

### What is not encoded

- **`ANC.DT.06` referral criteria** turn on second readings, on combinations across several exam
  results, and on gestational age — `"Fetal heartbeat present" = FALSE` *and* `"Gestational age" ≥
  20 weeks`. The inputs exist on the form, but the rule concludes rather than prompts, and it reads
  values from earlier contacts a single submission cannot see.
- **`ANC.DT.02` HEADSS assessment** fires on age under 19. Age lives on the patient record, not on
  the form, so no `visibilityCriteria` can reach it.
- **`ANC.DT.03` symptom counselling** distinguishes *current* from *persistent* symptoms, which is a
  comparison against the previous contact.
- **The five scheduling tables** (`ANC.S.01`–`S.05`) define when the next contact, test, counselling
  session, immunisation or prophylaxis dose is due. Recall and appointment concerns — Tamanu
  appointments, the registry's loss-to-follow-up threshold, and a `metric__` model for "due for a
  contact" — not form content.

## Annex D

Written as user stories. Nothing to encode in a form: it is a conformance checklist for the
deployment as a whole — audit trails, offline capability, role-based access, notifications. Worth
reading before anyone claims DAK compliance, since most of it is Tamanu platform behaviour rather
than anything this repo configures.

## Known gaps, in priority order

1. **Conditional visibility is almost absent.** Annex A expresses conditionality as prose in `Skip
   logic` plus a `Required = C` flag, which does not translate mechanically into
   `visibilityCriteria`. Each form therefore asks nearly every one of its questions every time,
   where the DAK intends much of it to appear only when relevant. It bites hardest on **Counselling
   and Treatment**, whose 39 questions cover eleven activities the DAK expects to be reached
   selectively. The four Annex B prompts are the only gated questions.
2. **`ANC Registration` duplicates the Tamanu patient record.** Unique identification, first name,
   last name, address and mobile phone number as survey questions are the anti-pattern Tamanu forms
   are meant to avoid. Either drop the survey and keep only `ANC contact number`, or convert the
   demographic questions to `PatientData` reads.
3. **The referral form asks for what Tamanu already knows.** `ANC.C.DE9`–`DE11` are the referring
   provider's name, cadre and facility, and Annex A's own `Calculation` for them reads "Same as
   end-user's profile". They are `Required = R`, so they are carried, but they want to be `UserData`
   reads.
4. **No calculated elements.** Thirty-two selected elements carry something in Annex A's
   `Calculation` column; twenty-one are pointers at a decision table rather than formulas, and the
   generator reads none of them. BMI (`ANC.B8.DE4`), weight gain (`ANC.B8.DE15`, `DE16`), parity
   (`ANC.B6.DE23`), previous fetal loss (`ANC.B6.DE32`) and preterm birth (`ANC.End.17`) are real
   expressions, and are emitted as ordinary questions a clinician types into. A `CalculatedQuestion`
   needs a separator-free code of its own, since a math.js `calculation` parses `a-b` as
   subtraction.
5. **Two screen headings read badly**, because they are the dictionary's own cells: *Create client
   record OR ANC.A8. Validate client details* on ANC Registration, where the activity cell names two
   activities, and a bare *ANC.End* on ANC Episode Outcome, where it names none.

## Indicator coverage

`annex_c_coverage.py` does not answer for this kit, and says so rather than guessing. It works by
comparing the data element labels an indicator's calculation quotes against the generated question
labels, which needs a kit that writes its calculations that way — the HIV kit's Annex C says
`COUNT of clients with "HIV status"='HIV-positive'`. This kit's Annex C states its fourteen
indicators in prose and quotes nothing:

> ANC.IND.1 — `COUNT of women whose gestational age ≤ 12 weeks at the time of first contact`

Fifteen questions carry an `ANC.IND.*` link from Annex A's own `Linkages to aggregate indicators`
column, covering ANC.IND.1, 2, 3, 4, 7, 9, 10, 11, 12 and 13; two more name an indicator in prose
without giving it a code. That column, not a computed coverage report, is what a `metric__` layer
over these forms should be read against.

## Terminology linkage

Annex A carries ICD-11, ICD-10, LOINC, ICHI, ICF and SNOMED CT codes per element. They are not used
yet: they are the raw material for the `map__omop_anc_dak` crosswalk seed that architecture decision
D1 prescribes ("OMOP vocabulary lookups via `map__omop_<domain>` seeds, populated on demand only").

## Fetching the annexes

`<domain>/annexes/` is gitignored: the DAK and its annexes are third-party publications WHO serves
at stable URLs. Fetch Annex A to where the generator looks for it — it prints this command itself
when the file is absent:

```bash
mkdir -p forms/who-dak/anc/annexes
curl -sL -o forms/who-dak/anc/annexes/WHO-SRH-21.1-eng.xlsx \
    https://iris.who.int/server/api/core/bitstreams/affcde61-7176-45c5-aac9-5503d2efc74d/content
```

Reproducibility rests on the checksum rather than on the bytes being in git. These forms were
generated from sha256 `eceb5d3594536c7010bfc7cc3894265701638f23f6dd27fca606bf1cbbe0d95f`, which
`dak_generator.py` verifies and warns about on mismatch — so a revised annexe announces itself
rather than quietly changing a form.

The legacy `/bitstream/handle/10665/339740/WHO-SRH-21.1-eng.xlsx` URL still returns HTTP 200, but
the body is a JavaScript shell rather than the file — a 755-byte download that looks like a success.
The direct bitstream URLs above were resolved through the DSpace API; `hiv/dak-conformance.md`
records the recipe. The four ANC handles are Annex A `10665/339740`, B `10665/339741`,
C `10665/339742`, D `10665/339744`.

## Rebuilding

```bash
cd forms/who-dak
FORMS_SKILL=../../../claude-plugins/plugins/tamanu/skills/build-tamanu-forms/scripts
python dak_generator.py --domain anc
python $FORMS_SKILL/build_program_xlsx.py \
    --spec anc/who-dak-anc_program.json --out anc/who-dak-anc_program.xlsx
```

The workbook rebuilds byte-identically from an unchanged spec, so a diff on the `.xlsx` means a diff
in the form rather than noise. The registry is declared in [`domain.py`](domain.py) rather than
carried across from the previous spec, so a regeneration cannot lose it.
