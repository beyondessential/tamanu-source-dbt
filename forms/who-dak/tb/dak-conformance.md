# DAK conformance — tuberculosis

What these forms take from the WHO DAK for tuberculosis, what they deliberately do differently,
and what the DAK specifies that a Tamanu form cannot hold.

## Source

Everything is generated by [`../dak_generator.py`](../dak_generator.py) from the kit's **core data
dictionary** (`TB DAK_core data dictionary.xlsx`, 481 labelled rows across the six `TB.*` process
tabs plus 138 more on `TB.Common`). It gives each data element an ID (`TB.C24.DE.1`), a label, a
data type, a `Required` flag, terminology codes (ICD-11 / ICD-10 / LOINC) and — for coded
elements — one child row per input option (`Multiple Choice Type = "Input Option"`).

Eighteen further rows come from the **decision-support logic**. Nothing is authored by hand.

**This kit is not published as IRIS Web Annexes.** IRIS carries the PDF (handle `10665/376631`)
and WHO ships the four components through its SMART guidelines implementation guide at
[smart.who.int/dak-tb](https://smart.who.int/dak-tb/). The component pages there serve whatever
the site last built, so [`domain.py`](domain.py) pins each component to WHO's own source
repository for that guide — `WorldHealthOrganization/smart-dak-tb` — at the **`v1.0.1` tag**,
whose `sushi-config.yaml` reads `version: 1.0.1` and `releaseLabel: release`. That is a
version-pinned path to the released bytes, which the component page is not; the component page is
recorded alongside it as `page`. See § Fetching the components.

## What the forms are

Six surveys, one per DAK business process: 165 questions from the dictionary plus 15 guidance
prompts and 3 patient issues, over 45 screens.

| | |
|---|---|
| Questions answerable in the form | 168 |
| — of which carry a data element id | 165 |
| — of which are copies of a shared-tab element | 64 (27 distinct elements) |
| — of which are decision-support issues | 3 |
| Coded questions carrying the kit's options | 82 (437 options) |
| Mandatory | 34 — exactly the kit's `Required = R`, per process |
| Linked to an Annex C indicator | 43 |
| Label / option / mandatory mismatches against the dictionary | 0, checked against an independent read of the dictionary |

- **Question codes** carry the data element id: `TB.C24.DE.1` → `whodaktb-c24-de-1`. A shared-tab
  element also carries the survey: `TB.Comm.DE.3` → `whodaktb-screening-comm-de-3`. See
  § The shared tab.
- **Labels and option strings** are the dictionary's, verbatim. Option strings are what land in
  `survey_response_answers.body`, so nothing downstream can compensate for strings that do not
  match the dictionary.
- **Screens are the DAK's own activities.** Four activity headings collide inside a survey because
  the kit gives two activities the same id under different wording — `TB.C11`, `TB.C12`,
  `TB.C16.1` and `TB.E4.1` each appear once alone and once paired with a later activity — and the
  second of each takes a numeric suffix, reported by the generator on every run.
- **`TB.F.Referral` is Tamanu's `referral` survey type**, so it lands on the facility Referrals
  tab; the rest are `programs`.
- **Two tabs are not forms.** `TB.Configuration` is deployment constants; `TB.Common` is where the
  shared elements are defined.
- Each question carries a `_dak` block in the spec — data element id, activity, data type, why it
  was selected, its indicator links, and `definedOn` where the element came from a shared tab.
  That is the crosswalk source, and is not written to the workbook, which has no column for it.

### The shared tab

The kit defines an element once and references it from every process that collects it. The six
process tabs define 132 elements in place and carry another 117 reference rows, each holding an
id, a label, a `Required` flag — and, where the type would go, the sentence
`Please check "TB.Common" tab for more data element details`.

| | |
|---|---|
| Reference rows on `TB.B.Screening` | 34 |
| on `TB.C.Diagnosis` | 37 |
| on `TB.D.TB Treatment` | 34 |
| on `TB.E.TPT` | 12 |

Read literally, a reference row is a question with no type, no options and no description, which
`tamanu_type` turns into a free-text box. That is how `Symptoms of TB`, `HIV status`, `mWRD test
result`, `Culture result` and `Site of TB disease` would all import: as text fields with the
kit's answer lists stripped off, on the forms whose whole purpose is to record those answers.

The reader therefore follows the reference. The definition supplies the type, the options, the
description and the quantity subtype; the reference row supplies the process's own `Required`
flag and conditionality, falling back to the definition's where it leaves them blank. Both
statements are the kit's: `TB.Comm.DE.57 Symptoms of TB` really is `Required = C` at screening and
`R` at diagnosis.

**A shared element appears on every form that collects it, and its code carries the survey.** A
question code becomes the global `pde-<code>` id and may appear once per workbook, so one unscoped
code would put `TB.Comm.DE.3 Body weight (kg)` on whichever form was built first and silently drop
it from the other three — and weight at screening, at diagnosis, at each monthly treatment
follow-up and for TPT dosing are four measurements, not one. `_dak.dataElementId` is
`TB.Comm.DE.3` on all four, so an Annex C calculation naming that element reaches every copy; a
`metric__` model over these forms has to union them deliberately rather than pick one.

### The selection rule

The six process tabs offer 249 elements once references are resolved. An element is included when
it is:

1. `Required = R` — the DAK says a system must capture it;
2. linked to an Annex C indicator — it feeds something reported;
3. named in the domain's shortlist.

That yields 165 questions. Rules 1 and 2 do little of the work: only 34 of the 249 are
`Required = R` and 161 are `Required = C`, the flag the kit uses for nearly all of its clinical
content. Without the shortlist the TPT form is seven questions — nothing on `TB.E.TPT` is
`Required = R` at all — and the diagnosis form records a resistance profile with half its
drug-susceptibility panel missing.

The shortlist names 91 elements. Each is an input to an encoded decision rule, an element an
Annex C calculation names, or a branch the care pathway turns on; `domain.py` gives the reason
per entry. Two groups are worth calling out:

- **The drug-susceptibility panel.** The dictionary links the isoniazid, fluoroquinolone,
  bedaquiline and linezolid results to indicators and leaves amikacin, pyrazinamide, clofazimine,
  delamanid and pretomanid unlinked. A panel carried by halves records a resistance profile the
  regimen tables cannot read, so all nine are carried.
- **`Case de-notified`.** Every indicator from `TB.IND.10` onwards excludes de-notified cases from
  its denominator, and the element is `Required = O`. A form with no way to record one cannot
  compute any of them.

## Deliberate divergence

| Divergence | Where | Why |
|---|---|---|
| A reference row is merged with its definition on the shared tab | `read_annex_a` in [`../dak_generator.py`](../dak_generator.py) | The alternative is 117 typeless free-text questions. The kit's own cell names the tab to follow |
| A shared element's question code carries the survey | `question_code` | `pde-<code>` is a global upsert key; one code cannot serve four contacts. The DAK id is unchanged in `_dak.dataElementId` |
| `TB.C3.DE.2` "High" and `TB.C3.DE.3` "Low" are read as options of `TB.C3.DE.1 Risk of MDR-TB` | `OPTION_ROWS` in [`domain.py`](domain.py) | The dictionary types them as nothing and marks them as nothing, which is indistinguishable from a section heading by rule. Annex B settles what they are: `TB.C16.1.DT.02` fires on `"Risk of MDR-TB" = 'High'` and `.03` on `= 'Low'` |
| `TB.Comm.DE.85` "Other" is read as an option of `TB.Comm.DE.73 Test sample type` | `OPTION_ROWS` | Same shape: ten sample types are marked `Input Option` and the eleventh is marked nothing at all |
| `TB.C3.DE.1 Risk of MDR-TB` is `Coding`, not `Boolean` | `ELEMENT_TYPES` | It has "High" and "Low" beneath it and Annex B compares it against both. Neither is true or false |
| `TB.A7.DE.38 Alternative contact relationship` is `Coding`, not `String` | `ELEMENT_TYPES` | It declares `Select one` and owns nine `Input Option` rows, which a `String` drops on the floor |
| `TB.B4.DT`'s guidance is shortened | `DECISION_SUPPORT` | Annex B's own wording runs to 276 characters and `survey_screen_components.text` is `varchar(255)`. The trim keeps both age branches and what each screens with |

Nothing else departs from the dictionary. Where the kit is inconsistent and the reader can settle
it by rule, it does so and reports it; where only the domain can settle it, the domain says so
above rather than the generator guessing.

## Decision support

A form can prompt; it cannot conclude. **This kit's decision tables are algorithms rather than
alerts**, which is the central limit on what is encodable: a Tamanu `visibilityCriteria` is a
conjunction of equalities over questions on the same form, and most of these tables are ordered
rule sets over inputs that span several forms.

### What is encoded

Fifteen guidance prompts and three patient issues, each gated on answers already on its form and
carrying the kit's own guidance text.

| Rule | Survey | Fires on | Prompt |
|---|---|---|---|
| `TB.B4.DT` | screening | `Risk group` includes PLHIV | Which screening algorithm WHO recommends, by age band |
| `TB.B7.DT` | screening | `TB screening result` = Screen positive for TB | Refer for diagnostic evaluation — **+ patient issue** |
| `TB.B7.DT` | screening | = Screen negative for TB | Assess the client for TPT |
| `TB.B7.DT` | screening | = Inconclusive | Consider repeating the test |
| `TB.C24.DT.01` | diagnosis | `Danger signs present` = Yes | Stabilise or transfer — **+ patient issue** |
| `TB.C7.DT.03` | diagnosis | `HIV status` = HIV-positive **and** `Seriously ill` = Yes | Perform a urine LF-LAM assay |
| `TB.C7.DT.16` | diagnosis | `Signs and symptoms of` includes Extrapulmonary TB | Test with Xpert or culture |
| `TB.C12.DT.02` | diagnosis | `mWRD test result` = MTB detected | Bacteriologically confirmed; interpret RIF resistance |
| `TB.C12.DT.04` | diagnosis | = Error/Invalid/No result | Repeat with a new specimen |
| `TB.C12.DT.31` | diagnosis | `Microscopy – sputum test result` = Positive | Bacteriologically confirmed; perform an mWRD |
| `TB.C12.DT.33` | diagnosis | `Culture result` includes Positive for TB | Bacteriologically confirmed; consider follow-on DST |
| `TB.C16.1.DT.02` | diagnosis | RIF resistance detected **and** `Risk of MDR-TB` = High | Treat as MDR-TB — **+ patient issue** |
| `TB.C16.1.DT.03` | diagnosis | RIF resistance detected **and** = Low | Repeat the mWRD test |
| `TB.E4.7.DT.08` | tpt | `TB infection test result` = Negative | A negative test does not rule out infection |
| `TB.E4.7.DT.09` | tpt | `TB infection test performed` = No | Testing is not a requirement for TPT |

Two patterns are worth naming, because both trade completeness for honesty:

- **Gating on a conclusion rather than reproducing the algorithm.** `TB.B7.DT` walks 57 rules over
  five inputs to reach a screening result, but every rule reaching a given result carries the same
  guidance for it. The prompt fires on the result the health worker recorded, which puts the kit's
  own words next to the answer that raised them without pretending the form computed it.
- **Stating an ungatable condition in the guidance.** `TB.B4.DT` and `TB.C24.DT.01` both turn on
  age, which Tamanu holds on the patient record rather than as an answer on the form. The prompt
  names the age band the rule applies to instead of gating on it. That shows the prompt more
  widely than the kit would: for danger signs the wider audience is safe, since danger signs in an
  adult warrant the same response.

### What is not encoded

| Table | What it does | Why a form cannot |
|---|---|---|
| `TB.D9.DT`, `TB.D10.DT` | Choose one of sixteen regimens from resistance, age, site, severity, pregnancy and drug intolerance | An ordered rule set over six inputs with inherited context between rows. A conjunction of equalities cannot express rule order, and there is no output to write |
| `TB.DT.14` | Weight-band dosing, 311 rows | A dosing table is a lookup, not a visibility condition |
| `TB.E6.DT`, `TB.E8.DT` | TPT regimen and dosage | The same shape, over age, weight, ART and medication interactions |
| `TB.B7.DT` (rules) | Reaches the screening result itself | 57 rules whose blank cells inherit the algorithm from the row above; the algorithm branch alone is 18 options |
| `TB.C7.DT` (most rules) | Which diagnostic test to use | Turns on CD4 thresholds and HIV clinical stage as ranges; only the two unconditional branches are encoded above |
| `TB.C12.DT` (most rules) | Bacteriological confirmation across combinations of LF-LAM, mWRD, microscopy and culture | 35 rules over five inputs; the four single-result conclusions are encoded above |
| `TB.C16.1.DT` (rules 05–20) | RIF resistance in the trace and indeterminate cases | Depends on age, on `Today() - "Year of previous TB treatment"`, and on the ultra melting-curve reading in combination |
| `TB.C24.DT` | The child treatment-decision algorithm | 22 rules over nine inputs including an age range and a score threshold |
| `TB.E3.1.DT` | Whether a TB infection test is relevant | Its inputs (`Risk group`, age) are on the screening form and the patient record, not on the TPT form |
| `TB.E4.7.DT` (most rules) | TPT eligibility | Reads `TB screening result`, `TB diagnosis result` and `Risk group`, which live on two other forms |
| `TB.D14.S` | The monitoring and follow-up schedule | A schedule, not a form: monthly sputum smear and culture through treatment, then at 6 and 12 months after it. Tamanu expresses this as tasks and appointments |

The last row is the largest gap in practice. The kit's schedule sheet is what turns a treatment
record into a cohort that can be followed, and nothing in a program form carries it.

## Annex D

Not encodable in a form, and not attempted: the functional and non-functional requirements
component is a specification of the *system* — access control, confidentiality of the TB record,
offline capability, export for national reporting. It is a checklist for a deployment's Tamanu
configuration and infrastructure, not content for a survey.

## Known gaps, in priority order

1. **`TB Treatment` is one form for the whole of treatment.** The kit's tab covers eligibility,
   regimen, initiation, monthly follow-up examinations and the final outcome, and
   `TB.D24.DE.1 Treatment outcome` is `Required = R` — so a mandatory outcome question sits on the
   form a nurse fills in at every monthly visit. The generator's model is one survey per process
   tab, so splitting it is a deployment's edit, not a regeneration.
2. **`TB Registration` duplicates the Tamanu patient record.** First name, last name, unique id,
   address, sex and telephone number are all `Required = R`, so the selection rule cannot leave
   them out. This is the same anti-pattern the FP kit's registration form has, and the same
   answer: trim the form before first import.
3. **`TB.C11.DE.12 TB diagnostic tool` imports as free text.** The dictionary types it `Coding`
   and gives it no options, so the list of available tools is country-configured (the same
   handling the HIV, ANC and FP kits get for their unlisted `Coding` elements). Annex B's
   `TB.C16.1.DT.05` compares it against `Xpert MTB/RIF Ultra`, so a deployment supplying the list
   should use the kit's spelling.
4. **`TB.Comm.DE.136 Reason treatment was not started` loses an option.** Its `Input options` cell
   reads "Died / Lost / Other" and the dictionary defines only two option rows, `TB.Comm.DE.137
   Died` and `TB.Comm.DE.138 Lost`; the third row is blank. Little is lost — the kit defines
   `Lost` as *"did not start treatment for any reason other than death"*, which already covers
   what `Other` would — but the form offers two options where the cell names three.
5. **No visibility criteria beyond the decision-support prompts.** Conditionality is prose in
   `Explain conditionality` plus a `Required = C` flag, so each form asks nearly every question
   every time. The diagnosis form is 61 questions over 14 screens on that basis.

## Indicator coverage

`python annex_c_coverage.py --domain tb`

| | |
|---|---|
| Indicators in the indicators component | 51 |
| Covered by the forms | 48 |
| Gap in the forms | 3 |

The three gaps are the indicators component's own label defects rather than missing questions:

- `TB.IND.31` quotes `"Linezolid susceptibility result"`, where the dictionary's label is
  `Linezolid susceptibility test result`. The question is on the diagnosis form.
- `TB.IND.33` and `TB.IND.34` quote `"TB Date of TB diagnosis"`, a stray prefix on
  `Date of TB diagnosis`. That question is on the diagnosis form too.

The check matches on the element label, because that is what the calculations quote, and a label
written differently reads as a gap. Widening the selection is the right response to a real gap;
loosening the comparison is not, so these three stay visible.

**Reading this kit's calculations needed two changes to the coverage check**, both in
[`../annex_c_coverage.py`](../annex_c_coverage.py):

- The kit writes alternatives as a chain — `("TB treatment history" = "New" OR "Recurrent" OR
  "Unknown")` — and uses `in` and `!=` alongside `=`. Every quote in such a chain is a value, not
  an element. Before this, 44 indicators read as gaps because their option strings were being
  looked for as questions.
- Its indicator table is divided into business processes and subject groups by rows that carry
  their heading in the id column, which read as indicators with an empty calculation. A row now
  needs an id *and* a numerator.

## Terminology linkage

The dictionary carries ICD-11, ICD-10 and LOINC codes per element, and the generator reads none of
them into the spec: Tamanu's `program_data_elements` has no column for a terminology code, and a
question's `code` is the DAK id. The crosswalk is the `_dak.dataElementId` in the JSON spec, which
maps a Tamanu question back to the row that carries every code the kit assigns.

Most rows read `Not classifiable in ICD-11` and `Not classifiable in ICD-10`, which is the kit's
own statement about its process data rather than a gap in the linkage.

## Fetching the components

The components are not committed — third-party spreadsheets WHO publishes at stable URLs, ignored
via `<domain>/annexes/`. [`domain.py`](domain.py) records the pinned URL and the component page
for each, and the sha256 of all four, which `dak_generator.py` verifies for the data dictionary
and warns about on mismatch — so a revised component announces itself rather than quietly changing
a form.

```bash
mkdir -p forms/who-dak/tb/annexes
cd forms/who-dak/tb/annexes
BASE=https://raw.githubusercontent.com/WorldHealthOrganization/smart-dak-tb/v1.0.1/input
curl -sL -o "TB DAK_core data dictionary.xlsx" \
    "$BASE/dictionary/TB%20DAK_core%20data%20dictionary.xlsx"
curl -sL -o "TB DAK_decision-support logic.xlsx" \
    "$BASE/decision-logic/TB%20DAK_decision-support%20logic.xlsx"
curl -sL -o "TB DAK_indicators.xlsx" \
    "$BASE/indicators/TB%20DAK_indicators.xlsx"
curl -sL -o "TB DAK_functional and non-functional requirements.xlsx" \
    "$BASE/system-requirements/TB%20DAK_functional%20and%20non-functional%20requirements.xlsx"
```

The tag is the release: `main` is a continuous integration build and at the time of writing reads
`version: 1.0.2`, `releaseLabel: ci-build`, with a data dictionary that differs from the released
one. Pin the tag, not the branch, and not the component page — the page serves whatever the site
last built.

## Rebuilding

```bash
cd forms/who-dak
FORMS_SKILL=../../../claude-plugins/plugins/tamanu/skills/build-tamanu-forms/scripts
python dak_generator.py --domain tb
python $FORMS_SKILL/build_program_xlsx.py \
    --spec tb/who-dak-tb_program.json --out tb/who-dak-tb_program.xlsx
python annex_c_coverage.py --domain tb
```

The generator reports every dictionary defect it absorbed and every judgement it had to make: the
117 shared-tab references it followed and where they came from, the four suffixed heading
collisions, the coded element with no multiple-choice type, and the coded element with no option
list. A run whose report changes is a revised component, and the checksum warning says so first.
