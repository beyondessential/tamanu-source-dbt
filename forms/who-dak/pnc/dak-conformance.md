# DAK conformance — postnatal care

What these forms take from the WHO DAK for postnatal care, what they deliberately do differently,
and what the DAK specifies that a Tamanu form cannot hold.

## Source

Everything is generated by [`../dak_generator.py`](../dak_generator.py) from the kit's **core data
dictionary** (`PNC DAK_core data dictionary.xlsx`, DAK version 1.0.0, 16 `PNC.*` tabs). It gives
each data element an ID (`PNC.B4b.DE.1`), a label, a data type, a `Required` flag, ICD-11 codes,
the decision-support tables it feeds, and — for coded elements — one child row per input option.

Eight further prompts come from the kit's own danger-sign decision tables. Nothing is authored by
hand.

**This kit is not published as IRIS Web Annexes.** The HIV and ANC kits ship four numbered annexe
spreadsheets as separate IRIS items; this one ships a PDF in IRIS and its four components as
downloads from WHO's SMART guidelines implementation-guide site. Same four components, a different
distribution — so `ANNEXES` in [`domain.py`](domain.py) records a `page` and a versioned `url`
rather than an IRIS handle per annexe.

## What the forms are

The kit becomes **two programs** — this one for the woman, [`../pnc-newborn/`](../pnc-newborn/README.md)
for the newborn — because a Tamanu survey submits against one patient and a program carries one
registry. Ten maternal surveys here, 110 questions over 13 screens; five neonatal surveys and 91
questions there. Everything below describes the kit, so it covers both.

| | |
|---|---|
| Questions answerable in the form | 110 here, 91 in the newborn program |
| — of which carry a data element id | 106 here, 88 in the newborn program |
| — of which are decision-support issues | 4 here, 3 in the newborn program |
| Coded questions carrying the kit's options | 75 here + 73 there (873 options; 1 repeat dropped) |
| Mandatory | 101 here + 88 there — exactly the kit's `Required = R` |
| Linked to an indicator | 1 |
| Label / option / mandatory mismatches against the dictionary | 0, verified on every build |

- **Question codes** carry the data element id: `PNC.B1.DE.1` → `whodakpnc-b1-de-1`.
- **Labels and option strings** are the dictionary's, verbatim. Option strings are what land in
  `survey_response_answers.body`, so nothing downstream can compensate for strings that do not
  match.
- **Screens are the kit's own activities**, and within an activity its section headings become
  in-screen headings.
- **Two subjects, two programs.** Every assessment tab is split `a` maternal / `b` neonatal, and
  that split becomes two Tamanu programs so each subject has a registry of its own. Reception is
  shared and stays with the mother, which is how the kit models arrival.
- **`PNC.B7` and `PNC.C1` are Tamanu's `referral` survey type**, so they land on the facility
  Referrals tab; the rest are `programs`.

### The selection rule

An element is included when it is `Required = R`, linked to an indicator, or named in the domain's
core shortlist. That yields 106. This kit publishes its dictionary as the core list — there is no
Component 5 shortlist to consult the way the HIV kit has one — and it marks 206 elements Required,
so rules 1 and 2 do nearly all the work.

The shortlist is used on two tabs, for one reason. **Every danger-sign element in the kit is
`Required = C`**, and the two on the reception tab carry no indicator link either. Rules 1 and 2
therefore produce a registration form that asks why the woman came and nothing else, and leave the
kit's own `PNC.A2.DT.01` and `PNC.A2.DT.12` triggers with nothing to fire on — the one thing
reception exists to catch. Four elements are named in [`domain.py`](domain.py): the maternal and
newborn danger signs at reception, the specific health concerns recorded with them, and the
maternal danger signs repeated on the physical exam, that last one because its newborn counterpart
`PNC.B4b.DE.1` is `Required = R` and one exam should not screen for danger signs while the other
does not.

## Deliberate divergence

| What | Where | Why |
|---|---|---|
| The 109 `Annotation` elements are not carried | `selected` in [`../dak_generator.py`](../dak_generator.py) | `Annotation` is a diagnosis the kit's decision logic concludes, carrying the guidance text that goes with it — `PNC.B6a.DE.1 Hypertension`, "Woman has hypertension – SBP of 140 mmHg or higher…". A form can prompt but not conclude, and there is no answer to store. They are instead the source of the registry's condition list |
| `PNC Configuration` becomes no form | `PROCESSES` in [`domain.py`](domain.py) | Site constants — population prevalence of gestational diabetes, HIV and schistosomiasis, and which services this site offers. One value per site, read by the decision logic; settings or a seed, not a survey |
| `Input option` is matched case-insensitively | `read_annex_a` in [`../dak_generator.py`](../dak_generator.py) | The kit writes `Input option` on 24 rows and `Input Option` on the rest. The difference is not cosmetic: an option row read as an element becomes a question of its own *and* takes the rest of its parent's options with it, so `PNC.A2.DE.74 Newborn's/infant's danger signs` would have imported with no options at all |
| A row with no data type and no multiple-choice type is a heading | `read_annex_a` in [`../dak_generator.py`](../dak_generator.py) | This kit heads its sub-sections that way — `PNC.B4a.DE.13 "Height and weight"` over height, weight and BMI — and marks the headings `Required`, so the flag cannot be part of the test. A kit that leaves a *real* element untyped names it in its own `ELEMENT_TYPES`, which supplies the type and lifts it out of the heading branch |
| `PNC.B3b.DE.54 "Feeding mode"` is typed via `ELEMENT_TYPES` | [`../pnc-newborn/domain.py`](../pnc-newborn/domain.py) | `Required = R` with five options immediately after it, but the dictionary leaves its own Data Type blank — read as a heading, it was dropping a mandatory question entirely and leaving its five options with no parent to attach to. The [`../pnc/`](../pnc/README.md) tabs need no such override; every untyped row there really is a heading |
| A heading closes whatever `Coding` parent was open | `read_annex_a` in [`../dak_generator.py`](../dak_generator.py) | Without this, `PNC.B4b.DE.52 "Malformation"` stayed the open parent straight through the "Vital signs and measurements" divider and eight `Quantity` rows, silently absorbing the unrelated stray option `PNC.B4b.DE.71 "Not feasible to collect measurement"` as one of its own — and the same defect a second time in the follow-up exam, `PNC.D4b.DE.54`. Neither stray option has a `Coding` parent of its own in the dictionary, so a closed heading orphans them instead of misattaching them; the run reports both |
| An `Input Options` cell naming another option of the same question falls back to the row's label | `resolve_option_strings` in [`../dak_generator.py`](../dak_generator.py) | Six rows across five questions carry an `Input Options` cell copied from the row above — `PNC.B2.DE.66 "Positive"` is given "Negative", the option directly before it, so an HIV-testing question imported with no way to record a positive result; `PNC.A2.DE.8 "History of convulsions"` is given "Heartburn", dropping a danger sign; `PNC.B2.DE.47`, `PNC.B2.DE.162` and two `PNC.B3a.DE.35` rows do the same. The cell is normally the string a health worker picks and is worth preferring, but it cannot be that when it repeats a string already on the question: two identical options collapse to one and the answer is lost rather than mislabelled. The row's own label is the other string the dictionary gives that row, so nothing is invented, and the run reports each fallback |
| A repeated option is carried once | `build_question` in [`../dak_generator.py`](../dak_generator.py) | `PNC.D4a.DE.76` lists "1–2 cm above the umbilicus" twice, in both columns, so there is no second string to fall back to and the dictionary is simply repeating itself. This is fatal rather than untidy: Tamanu writes one translatable string per option, and two identical ones collide on the `(string_id, language)` primary key inside a single bulk upsert, which Postgres rejects with *ON CONFLICT DO UPDATE command cannot affect row a second time* and which fails the whole workbook. First occurrence wins, order is kept, and the run reports every drop |
| Five heading codes carry a numeric suffix | `heading_code` in [`../dak_generator.py`](../dak_generator.py) | A heading code takes the DAK's own activity id so it does not move when a question is inserted, but this kit gives two *different* activities the same id five times — `PNC.B2. Record pregnancy, and labour and birth information` against the same phrase without the comma, `PNC.D3a. …follow up` against `…follow-up`, and three `OR`-joined pairs. The later of each takes a `-2` suffix in first-appearance order, and the run reports it; without that they would collide on one `pde-<code>` and the kit's row order would silently decide which survived |
| `Time` maps to Tamanu's `Time` question type | `tamanu_type` in [`../dak_generator.py`](../dak_generator.py) | `PNC.B2.DE.92 Time of childbirth` is the first `Time` element in any kit read here; without the mapping it would fall through to free text |

## Decision support

### What is encoded

| Rule | Survey | Fires on | Effect |
|---|---|---|---|
| `PNC.A2.DT.01` | PNC Registration | any of 11 maternal danger signs on `PNC.A2.DE.60` | Guidance to treat and refer urgently, plus a Tamanu patient issue |
| `PNC.A2.DT.12` | PNC Registration | any of 15 newborn danger signs on `PNC.A2.DE.74` | The same, for the newborn |

Both are anchored at reception because that is where the kit anchors them: the maternal
physical-exam tabs here reference `PNC.A2.DT.01` and `PNC.A2.DT.12` rather than defining triggers of
their own. The newborn program's physical exam does define one of its own — see
[`../pnc-newborn/dak-conformance.md`](../pnc-newborn/dak-conformance.md).

**`PNC.A2.DT.12` is emitted as three prompts.** Its fifteen danger signs serialise to 536
characters against a varchar(255) `visibility_criteria` column. Dropping signs to fit is not an
option when the point of the rule is that any one of them is urgent, so the list is split where it
crosses the limit and all three carry the same guidance. A newborn with signs in two chunks raises
two prompts, which is the right failure. The maternal list fits in one at 245 characters.

`No danger signs` and `Other (specify)` are excluded from every gate: the first is the option that
means the rule should not fire, the second carries no sign to act on.

### What is not encoded

- **The 109 diagnostic annotations.** Their conditions are expressions over several elements and
  across contacts — `PNC.B6a.DE.1` fires on `(("Urine dipstick result – protein"…` — and their
  output is a conclusion, not a prompt.
- **Anything turning on time since birth.** Much of the kit keys on the newborn's age in hours or
  days, which is derived from a birth timestamp rather than answered on the form.
- **The contact schedule.** When the next contact is due (24 hours, day 3, day 7–14, six weeks) is
  a recall concern — Tamanu appointments and the registry's loss-to-follow-up threshold — not form
  content.

## Known gaps, in priority order

1. **Both workbooks must be imported.** The kit is two programs, and a deployment running only the
   maternal half has no newborn record at all. Nothing enforces this — it is a runbook step.
2. **Newborn danger signs recorded at reception attach to the woman's submission**, because
   reception is one contact for both and the kit models it on the maternal tab. They are asked again
   on the newborn physical examination, where they attach to the newborn. A deployment that needs the
   reception answers on the newborn's record should add a reception form to the newborn program.
3. **Conditional visibility is almost absent**, for the same reason as in every other domain here:
   the kit expresses conditionality as prose plus a `Required = C` flag. The eight danger-sign
   prompts are the only gated content, and with 189 mandatory questions the cost is high — a
   clinician sees the newborn examination's 30 required questions whether or not the newborn is
   present.
4. **Every assessment appears twice.** `PNC.B3a` / `PNC.D3a` and `PNC.B4a` / `PNC.D4a` are the
   first-contact and follow-up versions of the same assessment, with different data element ids and
   therefore different question codes. Reporting over these forms has to union both.
5. **`Maternal Care and Treatment` and `Newborn Care and Treatment` are two questions each.** Their
   tabs hold 52 and 57 annotations respectively and almost nothing else, so what survives is the
   counselling-conducted flags. They are kept rather than dropped because those flags are
   `Required = R`, but a deployment may reasonably fold them into the exam forms.
6. **`PNC.A4` demographics are absent, and that is correct.** The kit's registration tab restates
   the woman's and the newborn's name, date of birth, phone and address. All are `Required = O`, so
   the selection rule drops them without needing to be told — unlike the ANC kit, whose equivalents
   are `Required = R` and do land on the form.

## Indicator coverage

`annex_c_coverage.py` does not answer for this kit. It compares the element labels an indicator's
calculation quotes against the generated question labels, which needs a kit whose indicator table
is a spreadsheet of that shape; this one publishes indicators as a component page and its
dictionary carries a single `Linkages to Aggregate Indicators` entry across all fifteen form tabs.
The kit's indicator definitions are at
<https://smart.who.int/dak-pnc/indicators.html>, and reading a `metric__` layer against them is a
separate job from these forms.

## Terminology linkage

The dictionary carries ICD-11 (2025 release) codes per element. They are not used yet: they are the
raw material for the `map__omop_pnc_dak` crosswalk seed that architecture decision D1 prescribes
("OMOP vocabulary lookups via `map__omop_<domain>` seeds, populated on demand only"). This kit
carries ICD-11 only, where the HIV and ANC kits also carry ICD-10, LOINC, ICHI, ICF and SNOMED.

## Fetching the components

`<domain>/annexes/` is gitignored: these are third-party publications WHO serves at stable URLs.
Fetch the data dictionary to where the generator looks for it — it prints this command itself when
the file is absent:

```bash
mkdir -p forms/who-dak/pnc/annexes
curl -sL -o "forms/who-dak/pnc/annexes/PNC DAK_core data dictionary.xlsx" \
    "https://smart.who.int/dak-pnc/v1.0.0/PNC%20DAK_core%20data%20dictionary.xlsx"
```

The other three components are the same URL with `PNC%20DAK_decision-support%20logic.xlsx`,
`PNC%20DAK_indicators.xlsx` and
`PNC%20DAK_functional%20and%20non-functional%20requirements.xlsx`.

**`../pnc-newborn/` needs its own copy of the core data dictionary**, at
`forms/who-dak/pnc-newborn/annexes/`, even though it is byte-identical to this one — each domain
resolves its annex path independently, and the generator does not share a fetch between them. Copy
the file rather than re-downloading it.

**Pin the version in the path.** `https://smart.who.int/dak-pnc/dictionary.html` serves the current
release and links both `v0.9.9` and `v1.0.0`; a bare filename next to the page follows whatever is
current. These forms were generated from `v1.0.0`, sha256
`fb01d97a20b846716a05db5d94d571d6459373c50d2f0d4962b69f783a454b3f`, which `dak_generator.py`
verifies and warns about on mismatch — so a revised component announces itself rather than quietly
changing a form.

## Rebuilding

```bash
cd forms/who-dak
FORMS_SKILL=../../../claude-plugins/plugins/tamanu/skills/build-tamanu-forms/scripts
python dak_generator.py --domain pnc
python $FORMS_SKILL/build_program_xlsx.py \
    --spec pnc/who-dak-pnc_program.json --out pnc/who-dak-pnc_program.xlsx
```

The workbook rebuilds byte-identically from an unchanged spec, so a diff on the `.xlsx` means a
diff in the form rather than noise. The registry is declared in [`domain.py`](domain.py) rather
than carried across from the previous spec, so a regeneration cannot lose it.
