# DAK conformance — immunization

What these forms take from the WHO DAK for immunizations, what they deliberately do differently,
and what the DAK specifies that a Tamanu form cannot hold.

## Source

Everything is generated by [`../dak_generator.py`](../dak_generator.py) from the kit's **core data
dictionary** (`IMMZ DAK_core data dictionary.xlsx`, 194 labelled rows on `IMMZ.D Administer
vaccine` plus 34 on `IMMZ.Z Vaccine library`, 17 on `IMMZ.C Client registration` and 27 on
`IMMZ.I Report generation`). It gives each data element an ID (`IMMZ.D.DE.19`), a label, a data
type, a `Required` flag, terminology codes (ICD-11 / ICD-10 / LOINC / ICHI / SNOMED GPS / WHO ATC)
and — for coded elements — one child row per input option (`Multiple Choice Type = "Input
Option"`).

Nine further rows come from the **decision-support logic**. Nothing is authored by hand.

**This kit merges its scheduling logic into the decision-support component** rather than
publishing a fifth annexe: 24 antigen tabs, each a decision table ending in a schedule that names
the due, overdue, expiration and completion dates for that antigen's doses.

**This kit is not published as IRIS Web Annexes.** IRIS carries the PDF (handle `10665/380303`)
and WHO ships the four components through its SMART guidelines implementation guide at
[smart.who.int/dak-immz](https://smart.who.int/dak-immz/). The component pages there serve
whatever the site last built, so [`domain.py`](domain.py) pins each component to WHO's own source
repository for that guide — `WorldHealthOrganization/smart-dak-immz` — at the **`v1.1.0` tag**.
That is a version-pinned path to the released bytes, which the component page is not; the
component page is recorded alongside it as `page`.

## What the forms are

Three surveys, each a slice of the one clinical tab: 41 questions from the dictionary plus six
guidance prompts and three patient issues, over six screens.

| | |
|---|---|
| Questions answerable in the form | 44 |
| — of which carry a data element id | 41 |
| — of which are decision-support issues | 3 |
| Coded questions carrying the kit's options | 20 (124 options) |
| — of which take their value set from `IMMZ.Z Vaccine library` | 1 (34 options) |
| Mandatory | 6 — exactly the kit's `Required = R`, per process |
| Linked to an Annex C indicator | 5 |
| Label / option / mandatory mismatches against the dictionary | 0, checked against an independent read of the dictionary |

- **Question codes** carry the data element id: `IMMZ.D.DE.19` → `whodakimmz-d-de-19`.
- **Labels and option strings** are the dictionary's, verbatim. Option strings are what land in
  `survey_response_answers.body`, so nothing downstream can compensate for strings that do not
  match the dictionary.
- **Screens are the DAK's own activities**, one per activity a survey takes.
- All three surveys are Tamanu's `programs` type. The kit has no referral process.
- Each question carries a `_dak` block in the spec — data element id, activity, data type, why it
  was selected, and its indicator links. That is the crosswalk source, and is not written to the
  workbook, which has no column for it.

### One tab, nine activities

Every other kit read here gives a business process its own tab. This one gives nine activities to
`IMMZ.D Administer vaccine` and separates them by activity id alone, so a process declares the
`activities` it takes and the reader slices the tab.

| | |
|---|---|
| Activities on `IMMZ.D Administer vaccine` | 9 |
| — taken as surveys | 6 (`D1`, `D2`, `D5`, `D7`, `D17`, `D18` across three surveys) |
| — not taken | `D13` (the dose record), `D20` and `D21` (digital certificate) |
| Rows naming two activities in one cell | 48, holding 19 elements (`IMMZ.D1 … OR IMMZ.D13 …`) |

A row naming two activities is taken under the half of the cell that named it for this survey.
Without that, `IMMZ.D1` opens two screens on the history form — one headed by the rows that name
only `D1` and one by the rows that also name `D13` — differing by wording that belongs to a
process the survey does not carry.

### The vaccine library

`IMMZ.D.DE.19 Vaccine type` is `Coding`, `Select all that apply`, mandatory, linked to
`IMMZ.IND.01` and the rest of the coverage indicators, and carries **no input options**. The kit
publishes its value set as a tab: `IMMZ.Z Vaccine library`, 34 rows naming one vaccine family
each, from `BCG vaccines` to `Pentavalent vaccines`.

Those labels are the strings the kit's own logic quotes — Annex B's `"Vaccine type" = "BCG
vaccines"`, Annex C's `COUNT of immunization events WHERE "Vaccine type" = "DTP-containing
vaccines"` — so they are the only values an indicator can match. `OPTION_SOURCES` in
[`domain.py`](domain.py) points the reader at the tab; the alternative is the kit's central
question importing as a free-text box that no indicator can read.

The tab's other 220 rows carry no label of their own: each is a further terminology code — a
second ICD-11 entity, another SNOMED concept — for the family above it, so the 34 labelled rows
are the whole value set.

### The selection rule

`Required = R`, or linked to an Annex C indicator, or named in the kit's core shortlist.

| | |
|---|---|
| Elements on the slices taken | 43 |
| Selected | 41 |
| — because `Required = R` | 6, two of them also indicator-linked |
| — because they feed an Annex C indicator | 5 |
| — because the shortlist names them | 32 |

The shortlist does most of the work here because the kit states every client characteristic its
decision tables read as `Required = C`. HIV status, ART status, immunological stability, clinical
wellness, preterm birth, birth weight, TB infection test result, dengue serostatus and the nine
antigen-specific dose types are all `C`, and none is linked to an indicator — so the first two
rules alone carry a history form that records what was given and nothing that governs what comes
next. Each entry traces to an input named by an Annex B antigen decision table.

## What the native vaccine module keeps

Tamanu records administered doses natively. This program does not repeat that, because two places
to write a dose is worse than one place that is missing something: coverage would have to be
computed from whichever source a deployment happened to use, with no rule saying which counts.

| Left to the native module | Why |
|---|---|
| `IMMZ.D13 Update client record` — vaccine brand, manufacturer, market authorization holder, batch number, expiry, dose quantity, country, administrative area, administering health worker, `Immunization event status`, `Reason vaccine was not administered`, `Disease targeted`, `Due date of next dose` | The dose itself. 55 rows, of which five are `Required = R` and would otherwise be carried by the selection rule without anyone choosing them |
| The products under each vaccine family | Tamanu's own vaccine reference data. The kit names families, not products |

What this program keeps is what Tamanu has no construct for: the history and risk factors the
schedule is computed from (`IMMZ.D1`), the recommendation status and contraindications
(`IMMZ.D2`, `IMMZ.D5`), counselling and the next visit (`IMMZ.D7`, `IMMZ.D18`), adverse events
(`IMMZ.D17`), and the registry.

The history form does carry `Vaccine type`, `Date and time of vaccination`, `Dose number` and
`Type of dose`. Those describe doses the client already had — commonly elsewhere, or before the
deployment ran Tamanu — which is what seeds a schedule. A dose given at this contact goes through
the native module.

## Deliberate divergence

| Divergence | Where | Why |
|---|---|---|
| A process is a slice of a tab rather than a whole tab | `activities` in [`domain.py`](domain.py), applied in [`../dak_generator.py`](../dak_generator.py) | The kit puts nine activities on one tab. Whole-tab reading yields one 194-row survey mixing history, contraindications, the dose record and adverse events |
| A row naming two activities is taken under the wording of the one this survey takes | `activity_parts` | Otherwise one activity opens two screens, differing by the half of the cell belonging to the other process |
| A heading code stops at the activity id, dropping the label word the kit joins on with a dot | `heading_slug` | `IMMZ.D1.Capture or update client history` would otherwise code as `…-act-d1-capture`, so a rewording by WHO moves the code and strands the old instruction row on re-import |
| `IMMZ.D.DE.19 Vaccine type` takes its options from `IMMZ.Z Vaccine library` | `OPTION_SOURCES` | Annex A gives the element no options; the kit's own logic quotes the library's labels as the values it compares against |
| `IMMZ.D.DE.254 Type of hepatitis B dose` is `Coding`, not `Codes` | `ELEMENT_TYPES` | It declares `Select one` and owns two `Input Option` rows, which `Codes` maps to free text and drops. Every sibling dose-type element on the tab is `Coding` |
| `IMMZ.C Client registration` is not a survey | `PROCESSES` | Name, sex, date of birth, caregivers, phone and address are the Tamanu patient record |
| `IMMZ.I Report generation` is not a survey | `PROCESSES` | Reporting period, disaggregation group and stock balances are aggregate reporting, which belongs to the metric layer |
| `IMMZ.D20` / `IMMZ.D21` are not surveys | `PROCESSES` | Issuing a verifiable digital certificate is a signing service, not a question a clinician answers |
| The registry's loss to follow-up is off | `REGISTRY` | The kit gives no overdue interval to set it from — see § What cannot be encoded |

## Decision support

Annex B holds 24 antigen decision tables reaching `IMMZ.D.DE156 Immunization recommendation
status` from age arithmetic, dose counts and immune status, with **498 distinct guidance strings**
between them, each naming an antigen and a dose number.

None of the rules is expressible as a `visibilityCriteria`, which is a conjunction of equalities
over answers on one form: the inputs are `Today's date − "Date of birth"` and counts over a dose
history the form does not hold. What is encoded is the guidance for the status a health worker
records, which is the same guidance every antigen table reaches for that status.

| Rule | Survey | Fires on | Prompt |
|---|---|---|---|
| `IMMZ.D2.DT` | status | `Immunization recommendation status` = Due | Vaccinate per schedule, check contraindications first |
| `IMMZ.D2.DT` | status | = Not due | Check for any vaccines due and inform the caregiver when to come back |
| `IMMZ.D2.DT` | status | = Complete | Schedule complete; check for any other vaccines due |
| `IMMZ.D5.DT` | status | = Contraindicated | Do not vaccinate; record the contraindication — **+ patient issue** |
| `IMMZ.D2.DT` | status | = Further evaluation needed | Clinical judgement is required; create a clinical note — **+ patient issue** |
| `IMMZ.D17` | aefi | `Type of reaction` is one of the six serious categories | Report through the national AEFI system and follow up — **+ patient issue** |

The serious-AEFI gate lists `Death`, `Life threatening`, `Disability`, `Hospitalization`,
`Congenital anomaly` and `Other important medical event (specify)` — the kit's own severity list,
which is the WHO definition of a serious AEFI. A non-serious reaction is recorded and no prompt
fires.

## Annex C coverage

39 of the kit's 49 indicators can be computed from these forms, checked by
[`../annex_c_coverage.py`](../annex_c_coverage.py).

Of the ten that cannot:

- **`IMMZ.IND.40`–`IMMZ.IND.43`** are closed and open vial wastage, vaccine stock availability and
  cold-chain equipment status. They read `IMMZ.I Report generation`'s stock elements, which are
  aggregate logistics reporting rather than a clinical form.
- **`IMMZ.IND.45`** is the immunization session completion rate, which counts
  `IMMZ.D.DE.1 Immunization event status` — part of the dose record, and so the native module's.
- **`IMMZ.IND.05`, `IMMZ.IND.36`, `IMMZ.IND.37`** and the `IMMZ.IND.[serial number]` template row
  are reported as gaps because the checker matches quoted Annex A labels and these computations
  state their numerators as prose spanning several clauses. Their inputs — vaccine type, dose
  number, type of dose and the date of vaccination — are all carried.
- **`IMMZ.IND.44`** is reported as a gap for the same reason: it compares `Reaction reported` to a
  quoted `"Yes"`, which the checker reads as a label rather than as the value. The AEFI form
  carries the reaction, its date, its manifestation, its type and its outcome.

26 quoted strings in the indicator computations sit on the right of a comparison, so the coverage
check reports them because it cannot tell a value from a label. Eighteen are `IMMZ.Z Vaccine
library` labels the forms now carry as `Vaccine type`'s option strings; the rest are `Completed`,
`Yes` and the six `[antigen name …]` placeholders the template indicator leaves to a deployment.

## What cannot be encoded

- **The schedule itself.** Due, overdue, expiration and completion dates are per antigen and per
  dose, anchored to date of birth or to the latest dose of that antigen. A Tamanu program registry
  has one loss-to-follow-up threshold over the whole registration, so there is nowhere to put
  them. The kit does not supply a single interval either: most of its antigen schedules answer
  *"when does the service become overdue?"* with *"to be determined by Member States; however,
  there is no recommended overdue date"*. Being overdue is therefore recorded as a clinical
  status, and automatic defaulter tracing needs a rule in the metric layer over the recorded
  status and dose history.
- **The recommendation itself.** See § Decision support: the form records the status the health
  worker reached, and cannot reach it.
- **Age-based gating.** Almost every antigen table branches on the client's age, which is on the
  patient record rather than on the form, so the branches are stated in guidance rather than
  gated on.
- **Verifiable digital certificates.** `IMMZ.D20` and `IMMZ.D21` require a signing key, a
  certificate schema version and an issuer — infrastructure, and Annex D's territory.
- **Simultaneous vaccination.** `IMMZ.IND.[serial number]` counts clients receiving two named
  antigens at one contact. `Vaccine type` is `Select all that apply`, so the data is there, but
  the indicator is a template the kit leaves for a deployment to instantiate per antigen pair.

## Fetching the components

The annexes are not committed. [`domain.py`](domain.py) records the URL for each, and the
generator prints the fetch command when Annex A is absent:

```bash
mkdir -p forms/who-dak/immz/annexes
curl -sL -o "forms/who-dak/immz/annexes/IMMZ DAK_core data dictionary.xlsx" \
    https://raw.githubusercontent.com/WorldHealthOrganization/smart-dak-immz/v1.1.0/input/dictionary/IMMZ%20DAK_core%20data%20dictionary.xlsx
```

The sha256 of Annex A, B and C is recorded in `ANNEXES`; the generator warns when the copy on
disk differs from the copy these artefacts were generated from, so a WHO revision announces
itself rather than quietly changing a form.
